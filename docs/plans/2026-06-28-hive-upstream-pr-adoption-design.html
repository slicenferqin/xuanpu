1. 结论与建议

建议采用“局部吸收，不整块搬运”的策略。 Hive 最近一个月的高价值改动集中在 Kanban、Claude CLI、Codex skills、SQLite 维护和终端稳定性。 玄圃当前已经形成 Field Context、Session HQ、Hub、XFP 和多 runtime 管理自己的主线，直接搬 Hive 大块功能会造成架构回退。 更合适的路径是把低耦合、高收益的稳定性修复和 Codex 能力拆出来，按玄圃现有 IPC、preload、Zustand、Field 体系重写。

P0Git/终端稳定性补丁

吸收 Hive #514 和 #516 的核心思想：branch watcher 改为 watch gitdir，PTY 去除继承的 COLUMNS/LINES，并补充终端诊断日志。

价值：减少 branch 状态错乱、TUI 尺寸异常、终端字体/渲染疑难问题。

P1Codex Skills Slash Picker

吸收 Hive #502 的产品能力：Codex session 输入 / 时展示 enabled skills，并以结构化 Codex UserInput 调用，而不是发送普通文本。

价值：让玄圃内 Codex 能直接使用本机技能生态，降低“知道有技能但不好调用”的摩擦。

P1SQLite 存储管理

借鉴 Hive #505 的 Settings Storage 面板：展示 DB/WAL 大小、预估可回收空间、执行安全压缩。

价值：玄圃 Field events、timeline、usage 长期累积后需要可见、可控的本地数据维护能力。

P2Markdown Task/Kanban 思路调研

Hive #508 和 #541 很大，不建议直接迁移。可以保留“任务卡文件化、diagnostics、watcher”的设计经验，后续用于玄圃自己的 Field Tasks。

价值：作为未来任务实体外部化的设计输入，不进入本轮实现。

2. 背景与上游 PR 评估

最近一个月 Hive 发布了 v1.1.14 到 v1.2.4，最新 release 为 v1.2.4，发布时间为 2026-06-22。合入 PR 中，和玄圃关系最密切的是多 agent 运行时、终端、Codex、Git watcher、本地数据维护和 Kanban/Ticket 工作流。

PR 主题 对玄圃价值 建议
#502 Codex skills to slash command picker 玄圃已有 Codex app-server 和 slash command UI，但缺少 skills/list 接入。 采纳，按玄圃 Codex runtime 重写。
#505 Database compression tools 玄圃 SQLite 数据量更可能增长，尤其是 Field event、timeline、usage。 采纳，但 orphan 规则必须按玄圃 schema 重新定义。
#514 Branch update propagation 玄圃当前 branch-watcher.ts 仍 watch HEAD 文件，存在同类问题。 优先采纳，低成本高收益。
#516 Terminal rendering stabilization 玄圃 pty-service.ts 继承 process.env，可能继承错误尺寸变量。 优先采纳，先做 env 与 diagnostics，字体增强可分期。
#525 Codex startup model validation 提醒玄圃检查 renderer-only 字段不要穿透到严格 RPC schema，错误要 toast。 对照审计，若存在同类问题则修。
#508 Markdown Kanban Mode 方向有价值，但依赖 Hive Kanban/RPC 架构，和玄圃当前主线不贴合。 只吸收设计思想，本轮不实现。
#535 / #542 pnpm dev 数据隔离及 revert 已被 Hive 回滚，说明方案或体验不稳定。 不采纳。

本地现状对照

  • src/main/services/branch-watcher.ts 当前 watch HEAD 文件，不是 gitdir。
  • src/main/services/worktree-watcher.ts 只在特殊文件存在时 watch MERGE_HEAD 等文件。
  • src/main/services/pty-service.ts 创建 PTY 时合并完整 process.env。
  • src/renderer/src/components/sessions/SlashCommandPopover.tsx 支持 slash commands，但没有 skill badge 或 structured skill select。
  • tsconfig.node.json 和 tsconfig.web.json 尚未设置 noEmit: true。

3. 产品需求

3.1 Git/终端稳定性

  1. 当用户在外部终端、agent 或 IDE 中切换/重命名分支时，玄圃侧栏应在 1 秒内刷新对应 worktree 的 live branch。
  2. 当 Git 通过原子写入替换 HEAD 文件时，watcher 不能因 inode 变化失效。
  3. 当进入 merge/rebase/cherry-pick 冲突态时，即使特殊文件启动时不存在，也应触发状态刷新。
  4. 内置终端和 agent terminal 不应继承父进程错误的 COLUMNS/LINES。
  5. 终端渲染问题需要能在主进程日志里看到关键诊断信息：backend、cols/rows、font stack、renderer fallback、TERM/COLORTERM。

3.2 Codex Skills Slash Picker

  1. 在 Codex session 中输入 / 后，slash picker 同时展示内置命令、agent slash commands 和 enabled Codex skills。
  2. 当 skill 名称和内置命令冲突时，内置命令优先，skill 保留但不覆盖已有行为。
  3. 选择 skill 后，玄圃应通过 Codex app-server 发送结构化 skill input，附带用户在 slash 后输入的参数。
  4. 当 Codex app-server 发出 skills 变化事件或 session 初始化完成后，picker 应刷新 skill 列表。
  5. 当 skills/list 失败时，UI 降级为现有 slash command 体验，不阻断普通 prompt。

3.3 SQLite 存储管理

  1. Settings 增加 Storage 区域，展示主 DB、WAL、SHM 和总占用。
  2. 用户可以点击 Analyze，看到可回收空间预估和主要来源：free pages、orphan rows、可清理临时/缓存记录。
  3. 用户点击 Compress 前必须二次确认，并展示风险提示：压缩期间会短暂阻塞本地数据库访问。
  4. 压缩必须保留有效项目、worktree、session、timeline、field memory、usage 数据。
  5. 失败时不得损坏现有 DB，必须保留原文件并给出可读错误。

3.4 非目标

  • 本轮不实现 Hive 的完整 Kanban/Ticket 系统，也不新增 Markdown Kanban 模式。
  • 本轮不把 Claude CLI terminal/handoff 作为整套 runtime 引入玄圃。
  • 本轮不改变玄圃既有 Field Context 注入协议和 Session HQ 信息架构。
  • 本轮不做远端同步或云端压缩，所有能力保持本地优先。

4. 技术架构设计

4.1 Track A: Git Watcher Hardening

修改 src/main/services/branch-watcher.ts：从 watch HEAD 文件调整为 watch worktree gitdir 目录，并监听 change、add、unlink。事件触发后依旧通过 git:branchChanged 发送 { worktreePath }，保持 renderer API 不破坏。

模块 改动 兼容性
branch-watcher.ts watch 目标从 HEAD 改为 gitDir，仅对 HEAD 及 refs 相关事件触发 debounce。 IPC payload 不变。
worktree-watcher.ts 始终把 MERGE_HEAD、REBASE_HEAD、CHERRY_PICK_HEAD 加入 watch 列表。 只增加状态刷新灵敏度。
renderer listener 收到 branch change 后强制刷新 live branch，并在 DB branch 与 live branch 不一致时触发 worktree sync。 需要检查现有 useWorktreeStatusStore 和 worktree list 监听逻辑。

4.2 Track B: Terminal Environment and Diagnostics

修改 src/main/services/pty-service.ts 的 env 构造：先复制 process.env，删除 COLUMNS、LINES，再应用 TERM、COLORTERM 和 opts.env。 这样 TUI 使用 node-pty 实际尺寸，而不是父 shell 的历史尺寸。

  • 新增 helper：buildPtyEnv(baseEnv, overrideEnv)，便于单测。
  • 新增 main log：PTY 创建时记录 TERM、COLORTERM、是否移除尺寸变量、cols/rows。
  • 新增 preload API：window.terminalOps.logDiagnostics(payload)，renderer 可把字体与 fit 信息写入主进程日志。
  • 字体增强分两期：第一期仅记录诊断，第二期再考虑 JetBrains Mono bundled fallback 和 Ghostty font-family 列表解析。

4.3 Track C: Codex Skills Slash Picker

玄圃已经有 codex-app-server-manager.ts、codex-implementer.ts 和 SlashCommandPopover。新增能力应放在 Codex runtime 层，不让 renderer 直接关心 app-server RPC 细节。

层级 新增能力 说明
Main service CodexImplementer.listSkills(sessionId) 定位 live Codex session/thread，调用 app-server skills/list。
Main service CodexImplementer.invokeSkill(sessionId, skillName, args, options) 构造 Codex structured UserInput[]，复用现有 prompt routing。
IPC/preload agentOps.listCodexSkills、agentOps.invokeCodexSkill 类型定义放入 src/preload/index.d.ts。
Renderer Slash command item 支持 kind: "command" | "skill" skill 使用独立 badge，键盘导航沿用现有 popover。

推荐把现有 SlashCommand 类型扩展为 discriminated union： SlashCommandItem。内置命令、agent slash command、Codex skill 在 UI 层统一排序和过滤，在执行层分发。

4.4 Track D: SQLite Storage Management

新增 src/main/ipc/storage-handlers.ts 和数据库服务方法。压缩流程必须以“原 DB 不被破坏”为第一原则。

  1. getStorageStats()：返回 DB/WAL/SHM 文件大小、page count、free list、最近 checkpoint 时间。
  2. previewCompaction()：只读扫描 orphan rows，返回可回收估算，不修改数据库。
  3. compactDatabase()：暂停写入入口，checkpoint WAL，关闭连接，复制 DB 到临时文件，在临时文件执行 prune/VACUUM，校验后原子替换。
  4. 完成后重新打开 DB，恢复 WAL/foreign keys，发出 renderer toast 和 telemetry 事件。

orphan 规则首版只处理低风险对象：没有父 session 的 session_messages / session_activities，以及已经明确标记可清理的临时表。Field memory、pinned facts、usage entries 不进入自动删除范围。

5. 实施计划

阶段 范围 产出 建议测试
M1 Git watcher hardening 修复 branch watcher、特殊 Git 文件 watch、branch refresh。 branch-watcher、worktree-watcher、worktree store focused tests。
M2 PTY env 与 terminal diagnostics 移除继承尺寸变量，增加诊断 IPC 和日志。 pty-service 单测、TerminalView smoke、手动打开 vim/top/claude/codex TUI。
M3 Codex skills slash picker skills/list、skill item UI、structured invocation、skills changed refresh。 Codex implementer、IPC routing、SlashCommandPopover、SessionView focused tests。
M4 Storage settings storage IPC、DB stats/preview/compact、Settings UI。 database compaction tests、preload type tests、Settings UI tests、手动备份恢复验证。
M5 Codex payload/error audit 确保 renderer-only model fields 不穿透严格 RPC，connect/prompt failure toast。 Codex startup regression tests。

推荐提交拆分

  1. fix: harden branch watcher against git head rewrites
  2. fix: normalize pty environment and add terminal diagnostics
  3. feat: surface codex skills in slash command picker
  4. feat: add sqlite storage stats and compaction settings
  5. test: cover codex payload validation and startup errors

6. 测试与验收

6.1 自动化测试

  • pnpm vitest run test/path/to/branch-watcher.test.ts：模拟 HEAD 原子替换、unlink/add/change。
  • pnpm vitest run test/path/to/pty-service.test.ts：验证 COLUMNS/LINES 被移除，override env 仍能生效。
  • pnpm vitest run test/phase-6/session-7/slash-commands.test.tsx：扩展 skill item 过滤、badge、优先级。
  • pnpm vitest run test/path/to/codex-skills.test.ts：覆盖 skills/list、structured skill invoke、失败降级。
  • pnpm vitest run test/path/to/database-compaction.test.ts：覆盖 preview、临时 DB VACUUM、失败不替换原 DB。

6.2 手动验收

  1. 在外部终端执行 git switch -c test-branch，玄圃侧栏应刷新当前 branch。
  2. 在外部终端执行 branch rename，玄圃 worktree 名称或 branch 展示不应停留在旧值。
  3. 在玄圃内置终端启动 vim、top 或 Codex/Claude TUI，首次布局不应出现明显错位。
  4. 在 Codex session 输入 /，能看到 skill badge；选择 skill 后 Codex 收到 structured input。
  5. 关闭 app 前后执行 Storage Analyze/Compress，数据仍可正常读取，session history 不丢失。

6.3 不可接受结果

  • 压缩失败导致 DB 无法打开。
  • Codex skills/list 失败阻断普通 prompt 发送。
  • watcher 增强导致大量重复刷新或 CPU 持续升高。
  • 终端 env 改动导致用户显式传入的尺寸变量被覆盖。

7. 风险与决策点

决策 1：是否立即做 Storage Compact？

建议先做 getStorageStats 和 previewCompaction，压缩按钮放到 feature flag 或实验区。 原因是玄圃 DB 语义比 Hive 更复杂，Field memory 和 usage 数据不能被误删。

决策 2：Codex skill 是否进入统一 slash command 模型？

建议进入统一模型，但执行路径必须区分。UI 层统一展示和过滤，执行层按 kind 分发，避免把 skill 当普通 slash text 发送。

决策 3：Markdown Kanban 是否进入路线图？

本轮不做。若未来要做，应以玄圃自己的 Field Task 或 XFP 任务实体为中心，而不是引入 Hive Kanban 的内部模型。

开放问题

  • Codex app-server 的 skills/list 响应结构在当前玄圃锁定版本中是否稳定，需要用真实 Codex 版本验证。
  • Storage Compact 是否需要自动备份一份 xuanpu-before-compact-YYYYMMDD.db，还是只依赖临时文件原子替换。
  • 终端字体增强是否要引入 bundled font 文件，还是先只做 diagnostics 与环境修复。
  • branch watcher 修复是否需要同步影响 Hub/mobile 的 live branch 订阅语义。

最终推荐

第一批实施只做 M1、M2、M3。M4 Storage Compact 先落 stats/preview，压缩动作经过一次手动 DB 备份验证后再开放。 这条路径能快速吸收 Hive 最近一个月最确定的收益，同时不把玄圃拖回 Hive 的 Kanban/Claude CLI 架构分支。
