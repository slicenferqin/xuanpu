0 · 关键纠偏：turn 内不重建上下文

上一份规划隐含一个容易被误读的命题——「每次 provider call 都从 durable state 重建一个小而准的上下文」。 这既不是当前实现，也不应成为 turn 内部的目标。把它当成现状或目标，都会走偏。

代码事实（已考证）：玄圃侧 packContext() 在一个用户 turn 内 只调用 1 次（xuanpu-agent-implementer.ts:554），仅当 fillRatio≥0.4 触发 soft shrink 时 repack 第 2 次（:578）。piSession.prompt() 也只调一次（:606）。 turn 内那些「读文件 → 编辑 → 跑命令」的多次 LLM call，发生在 pi-agent-core 的 agentLoop 内层循环里， 在同一个累积的 messages 数组上追加 assistant + toolResult，而非重建。

内层每次 call 前唯一会动上下文的接缝是 transformContext 钩子 （context/budget-manager.ts:138），而它平时是 no-op （return messages 原样返回），只在 fillRatio≥0.8 时紧急裁掉最老的 toolResult。

为什么 turn 内必须保持累加：provider prompt cache 命中依赖前缀逐字节稳定。 内层累加天然 cache 友好——第 N 次 call 的前缀 = 第 N-1 次的全部 + 新增。 若改成「每次 call 重新 derive 上下文」，每次前缀都可能变 → cache 必然 miss。 这与规划 P3 想要的「cache 命中率优化」直接冲突。原规划没有点破这个张力。

因此本设计确立一条贯穿全文的原则：

重建只发生在 epoch 边界，turn / epoch 内保持消息累加。 一个 epoch 内累加吃满 cache；epoch 收尾做一次「压缩 + checkpoint」， 下一个 epoch 从压缩后的 durable state 起一个新的稳定前缀。这正是把现有 soft shrink → freeze → repack 机制（implementer.ts:566-590） 从「fillRatio 阈值触发」升级为「epoch 节奏驱动」，而不是改造内层 agentLoop。
补充约束：当前实现还有一个 pre-flight freeze（implementer.ts:427-430）， 每 turn pack 前都可能新增 field_episode_blocks。如果 frozen episodes 被放进 stable prefix， 但 freeze 仍按每 turn 触发，stable prefix 仍会频繁变化。因此 S1/S2 必须把 freeze 节奏迁到 epoch / soft-shrink 边界，或延迟新 episode 进入 stable prefix 的时机。

1 · 运行时模型与层级

四个层级，自顶向下。只有最外两层是新增治理对象，内两层沿用现状。

层级定义边界标志实现归属
Task Run 用户一句话触发的完整任务，可跨多个 epoch、可跨应用重启恢复 用户输入开始 / 交付或显式终止 新增 agent_task_runs + 编排层
Epoch task run 内的一个工作周期：若干 LLM call + 工具 + 1 个 checkpoint + 1 个 next-step checkpoint 写入 / 压缩触发 / watchdog 新增 agent_epochs，复用 freeze+repack
Turn 一次 piSession.prompt() 调用；当前 = 一个用户回合 prompt() 开始 / agentLoop 结束 已有 agent_turns（schema v34）
Provider Call agentLoop 内层一次 LLM 请求 请求发出 / usage 事件回来 已有 agentLoop，改 记账粒度 
Task Run  (agent_task_runs)          ← 可恢复、可暂停、可续 lease
  └─ Epoch 1  (agent_epochs)         ← 收尾写 checkpoint + 压缩
  │    └─ Turn  (agent_turns)        ← piSession.prompt() 一次
  │         ├─ Provider Call 1       ← agentLoop 内层，messages 累加
  │         ├─ Provider Call 2       ← 前缀 = call1 全部 + 新增（cache 命中）
  │         └─ Provider Call N
  └─ Epoch 2  (agent_epochs)         ← 从 epoch1 的 checkpoint 起新稳定前缀
       └─ Turn ...
关于 Turn 与 Epoch 的关系：当前一个用户输入 = 一个 turn = 一次 prompt。 引入 epoch 后，多数短任务仍是「1 task run = 1 epoch = 1 turn」，零额外开销。 只有长任务（agentLoop 跑很多 call、fillRatio 顶到压缩线）才会在内部切出多个 epoch。 Epoch 不是强制每 turn 都建——它是「压缩 + checkpoint」事件的命名容器。
必须明确 continuation 机制：piSession.prompt() 返回时，当前 agentLoop 已经结束。 真正能跑 1–2 小时的 task run 需要一种继续机制： Agent.followUp() / getFollowUpMessages 继续同一 Agent loop，或由外层 task runner 发 synthetic turn 开启下一段。两者会影响 cache、usage、checkpoint 和 UI 边界；本文后续默认优先采用 follow-up 队列，因为它能保持 epoch 内 messages 累加和 provider cache 语义。

better-sqlite3 / SQLite 迁移注意：ALTER TABLE ADD COLUMN 虽然可添加 nullable REFERENCES，但如果 down 脚本只 drop agent_task_runs / agent_epochs， child table 会留下引用已删除 parent table 的 FK，后续 PRAGMA foreign_keys=ON 写入可能失败。 因此本设计选择新增列不带 FK；down 可安全 drop 两张新表并保留空列。若要 DB 级 FK， 必须在 up/down 都 rebuild agent_turns / agent_turn_usage_events / field_session_checkpoints。

4 · 稳定前缀重构与 actualPrefixHash

这是规划诊断最准的一处，也是 cache 命中不稳的根因。现状有两个问题。

问题 A：anchor 含 volatile JSON

implementer.ts:540-553：真实发送给 provider 的 anchor 文本里包含 JSON.stringify(compileResult.packet, null, 2)，其中带 packetId、 capturedAt 等每轮变化的字段。而 prefixSeed 却只取 version+instruction （注释 :547 明说「no packetId, capturedAt, or volatile JSON」）。 于是 prefixHash 看起来稳定，真实前缀却每轮都变，provider 永远 cache miss。

问题 B：prefixHash 不来自真实 provider messages

context-packer.ts:183 的 prefixHash = djb2Hash(prefixSeed + frozenEpisodeText) 是一个旁路 seed，不是对真正发出的 providerContextMessages 前 N 条做 hash。 buildProviderRequest（provider-request-builder.ts:74）虽然对完整 messages 算了 providerRequestHash，但那是整体请求 hash，无法区分「稳定前缀」和「易变后缀」。

问题 C：pre-flight freeze 会让 frozen episodes 每 turn 变化

xuanpu-agent-implementer.ts:427-430 当前在 packContext 前每 turn 调 freezeOldConversationTurns()。当旧消息满足 keepRecentMessages=6 / minFreezeMessages=4 时，它会写新的 field_episode_blocks。 如果 frozen episodes 被放入 stable prefix，但 freeze 仍按每 turn 触发，stable prefix 会被新 episode 持续改变。stable prefix 重构必须同步把 freeze 改成 epoch 边界驱动，或让新 episode 在下一个 epoch 才进入 stable prefix。

4.1 重构方案：显式分区 + 真实前缀 hash

把 packContext 的产物明确切成 stable prefix 与 volatile suffix 两段， 各自独立 hash。zone 重排后顺序为：

序zone归属缓存语义
1system prompt（工具原则 / 安全边界）stable prefix
进 actualPrefixHash		跨 turn 不变
2task ledger（objective / 已完成 / 当前阶段）仅 checkpoint 时变
3frozen episodes（已冻结历史摘要）仅 freeze 时追加
4pinned facts用户手动改才变
5retrieved episodes（按需检索）volatile suffix
不进前缀 hash		每轮可能不同
6working set（最近 N turn）持续增长
7live field packet（git / focus / 现场）高频变化
8current request（用户本次输入）永不压缩
关键修复：把 live field packet（含 volatile XFP JSON）从 anchor（zone 1）移到 zone 7， 不再污染稳定前缀。anchor 只保留真正不变的规则文本。同时把 pre-flight freeze 移出每 turn pack 前路径， 避免 frozen episodes 反过来污染 stable prefix。

4.2 actualPrefixHash 计算

// context-packer.ts — 替换 djb2 旁路 seed
export interface ContextPackerDecisions {
  // ...
  /** 对真实 stable-prefix messages 的 sha256，stable 区无变化则跨 turn 恒定 */
  actualPrefixHash: string
  /** 触发 prefix 变化的原因，用于 cache-miss 归因 */
  prefixChangeReason?:
    | 'model' | 'tool_schema' | 'ledger' | 'episodes' | 'pinned' | 'none'
}

// 计算：对 zone 1-4 的渲染结果（去掉 timestamp）做 canonical sha256，
// 复用 provider-request-builder.ts:stripVolatileFields 的同款规范化逻辑，
// 保证与真实 provider payload 一致。
function computeActualPrefixHash(stablePrefixMessages: XuanpuPiPromptMessage[]): string {
  const canonical = stableStringify(stripVolatileFields(stablePrefixMessages))
  return createHash('sha256').update(canonical).digest('hex')
}

4.3 cache-miss 归因

每次 provider call 回来后，比对本次 actualPrefixHash 与该 task run 上一次的值。 不同则记录 prefixChangeReason（diff 哪个 zone 的 hash 变了）。写入 agent_turn_context_snapshots.decisions_json（复用现有列，无需建表）。 Session HQ 据此展示 task run 级 cache 趋势与 miss 原因，而非孤立 POST 行。

5 · per-call usage 记账

现状 agent_turn_usage_events 已是 event-keyed 原子 ledger （turn-repository.ts:315，唯一索引 (turn_id, source_event_id)）， schema 本身就支持每个 provider call 一行——只是当前写入粒度是 turn 聚合。 本节把写入下沉到 agentLoop 的每次 call。

5.1 事件来源

pi-agent-core 在每个 assistant message_end 事件上携带 usage （runtime.ts:269 已捕获 event.message?.usage）。 在 runtime.ts 的 subscribe 回调里，为每个带 usage 的 message_end 触发一次记账回调， 而不是只在 turn 结束聚合一次。

7 · epoch 划分与 checkpoint 写入

epoch 是「压缩 + checkpoint」的命名容器。核心是把现有 soft-shrink 逻辑 （implementer.ts:566-590）的触发点，从「单纯 fillRatio≥0.4」升级为显式 epoch 收尾。

7.1 epoch 边界判定

在一个 turn 的 agentLoop 结束后（piSession.prompt() 返回处，implementer.ts:606 之后），评估是否需要切 epoch：

function shouldCloseEpoch(ctx: {
  fillRatio: number              // packedContext.decisions.fillRatio
  providerCallCount: number      // 本 epoch 累计 call 数
  elapsedMs: number
  autonomy: TaskRunAutonomy
}): { close: boolean; reason: EpochCloseReason } {
  if (ctx.fillRatio >= 0.4)            return { close: true, reason: 'compact' }
  if (ctx.providerCallCount >= 12)     return { close: true, reason: 'checkpoint' }
  if (ctx.autonomy === 'short')        return { close: true, reason: 'turn_end' }
  // long/overnight：未达压缩线则继续累加同一 epoch（吃 cache）
  return { close: false, reason: 'turn_end' }
}
短任务零开销：autonomy='short'（默认）每个 turn 结束即 close epoch， 行为等价于现状「1 turn = 1 回合」，只是多写了一条 epoch 记录。长任务才会让 epoch 横跨多 turn。

7.1b continuation：长任务如何继续

epoch 边界判定发生在 agentLoop 将要 yield 的位置，而不是只能等 piSession.prompt() 完全返回后再决定。 优先实现方式是接入 pi-agent-core 的 onBeforeYield / getFollowUpMessages： 

onBeforeYield:
  evaluate epoch / lease / watchdog
  if shouldContinue:
    agent.followUp({ role: 'user', content: nextStepInstruction })
  else:
    allow agentLoop to end and mark turn/task state

这样同一 epoch 内仍保持 messages 累加，provider cache 语义不变；只有 epoch close 后才通过 checkpoint + repack 开启新的稳定前缀。外层 synthetic turn 作为备用方案，只用于跨重启恢复或明确需要重建 provider context 的场景。

7.2 checkpoint 写入（复用 field_session_checkpoints）

epoch close 且 reason ∈ {checkpoint, compact} 时，写一条 checkpoint。 不新建表——复用 field_session_checkpoints，填入 §3.2 新增的 epoch_id / task_run_id，并放宽其 source CHECK 约束： 

-- v35 同时 ALTER：source 增加 'epoch' 取值
-- SQLite 无法直接改 CHECK，需 rebuild 表或在迁移中重建。
-- 现状 CHECK (source IN ('abort','shutdown')) → ('abort','shutdown','epoch')
SQLite CHECK 约束变更：需走「建新表 → copy → drop 旧 → rename」的标准 rebuild。 field_session_checkpoints 数据量小（每会话个位数），rebuild 成本可忽略。 迁移脚本需保留现有 UNIQUE 索引 (worktree_id, packet_hash)。
checkpoint 隔离必须先做：现有 getLatestCheckpoint(worktreeId) 会返回 worktree 最新 checkpoint，不区分 source / purpose。epoch checkpoint 进入同表后，必须让默认 verifier 只读取 checkpoint_purpose='resume'，而 task-run runtime 通过 task_run_id / epoch_id 读取 checkpoint_purpose='task-epoch'。否则任务内部 checkpoint 会覆盖 abort/shutdown resume 语义。

checkpoint 内容字段（summary / current_goal / next_action / hot_files_json / hot_file_digests_json） 已覆盖规划 TaskCheckpoint 的 objective/completed/inProgress/blockers/touchedFiles/nextStep。 completed / inProgress / blockers 三个列表序列化进现有 summary 或扩一个 progress_json 列即可，无需重设计。

7.3 下一个 epoch 的起点

新 epoch 的第一个 turn 调 packContext 时，task ledger（zone 2）来自刚写的 checkpoint （已有 buildCurrentGoalFromCheckpoint / buildAnchorSection，implementer.ts:421-422）， working set（zone 6）被 freeze 清空、改由 frozen episodes（zone 3）承载。 于是新 epoch 的稳定前缀重新固定，actualPrefixHash 在该 epoch 内保持恒定。

8 · watchdog（epoch 级）

watchdog 挂在 epoch 上，三类，全部可复用现有信号或低成本新增：

watchdog信号来源触发动作归属
tool-storm StormDetector（runtime.ts:124，windowSize 5 / threshold 3） 已有去重；超阈值时 close epoch，reason='watchdog' 复用
no-progress 连续 N 个 provider call 无 touchedFiles 变化 / 无新工具结果 暂停 task run，status='paused'，等用户介入 新增 计数器
provider-failure runtime.ts:369 已捕获 errorMessage / 首事件超时 记 failure，连续达阈值则 fail epoch 扩展
规模匹配（记忆约束：并发活跃会话 ≤5、有人值守）：watchdog 保留，因为它防的是单会话内 agentLoop 跑飞，与并发数无关。

8.1 execution lease 与 epoch 是正交的两个轴

纠正一处早期设计错误：lease 自动续期不是「仅 overnight 才需要」。 只要一个自主任务活过一个 lease 窗口（哪怕只是 1–2 小时的任务），就必须续期， 否则会在窗口边界被硬停在半途。lease 不是按任务总时长分级的开关，而是一个固定墙钟周期的 「是否继续」决策点。

lease 和 epoch 由不同的轴驱动，互不替代——任何活过一个窗口的任务两者都需要：

轴驱动因素节奏决策内容
epoch 上下文压力（fillRatio / callCount） 不固定：工具风暴时 2 分钟一个，长思考时 20 分钟一个 「该压缩 + 写 checkpoint 了吗」
lease 墙钟（固定周期，如 20 min） 固定：每窗口边界评估一次 「进展 / 成本 / 风险 都 OK，要继续吗」

一个 1 小时的任务可能在一个 lease 窗口内烧穿多个 epoch（工具密集）， 也可能在一个 epoch 里横跨多个 lease 窗口（长思考、少工具）。两者频率无关，所以都要保留。

8.2 续期判定：续期始终发生，变化的是闸门

自动续期对任何 autonomy 都会发生（short 除外，它本就预期单窗口内完成）。 随 autonomy 变化的是续期的闸门严格度，而非续期是否发生： 

type LeaseDecision =
  | { action: 'renew'; nextExpiresAt: string }
  | { action: 'pause'; reason: string }     // 等用户介入
  | { action: 'ask'; prompt: string }       // 弹审批点

function evaluateLeaseAtBoundary(run: AgentTaskRun, signals: {
  noProgressCalls: number          // 连续无进展的 call 数
  costSinceStart: number
  hasPendingRiskyWrite: boolean    // 等待确认的高风险写操作
}): LeaseDecision {
  switch (run.autonomy) {
    case 'short':
      // 预期单窗口内完成；活过窗口本身就是异常信号
      return { action: 'pause', reason: 'short task exceeded one lease window' }

    case 'long': {                 // ← 你说的 1–2 小时场景：自动续期
      if (signals.noProgressCalls >= NO_PROGRESS_LIMIT)
        return { action: 'pause', reason: 'no progress' }
      if (signals.costSinceStart >= LONG_COST_CEILING)
        return { action: 'ask', prompt: 'cost ceiling reached, continue?' }
      if (signals.hasPendingRiskyWrite)
        return { action: 'ask', prompt: 'risky write pending approval' }
      return { action: 'renew', nextExpiresAt: addMinutes(now, LEASE_WINDOW_MIN) }
    }

    case 'overnight': {            // 闸门更宽：成本上限为主，容忍更长 no-progress
      if (signals.costSinceStart >= OVERNIGHT_COST_CEILING)
        return { action: 'ask', prompt: 'overnight cost ceiling reached' }
      return { action: 'renew', nextExpiresAt: addMinutes(now, LEASE_WINDOW_MIN) }
    }
  }
}
为什么单会话有人值守也需要：lease 的价值不是清理孤儿进程（那才和并发数相关）， 而是在用户没盯屏的那 1–2 小时里，周期性地用「进展 / 成本 / 风险」闸门替用户做"继续吗"的决定。 人不会每秒都看，这正是 long autonomy 任务必须自动续期的原因。续期边界也是天然的成本/进展汇报点。

实现落点：lease 边界评估挂在 epoch close 之后顺带触发（已是墙钟意义上的自然停顿点）， 或由一个 20min 的轻量定时器驱动；renewLease 已在 §3.3 repository 接口中预留。

12 · 非目标

  • 不改造 agentLoop 内层累加模型——turn / epoch 内保持消息累加以吃满 provider cache。
  • 不让「每次 provider call 重建上下文」，那会与 cache 优化目标冲突。
  • 不新建与 field_* 并行的第二套记忆真相；checkpoint/episode/pinned/working set 全部复用现有表。
  • 不靠把 150k 调到 500k 掩盖上下文治理；窗口是单 call 上限，治理靠 epoch + 压缩 + checkpoint。
  • 不把 provider session state 当记忆来源；它仅作 cache/latency 优化，且当前保持 disabled。
  • 不把 short autonomy 任务默认限制在固定分钟数或固定 call 次数内；硬上限只属于单次 provider call 窗口。
  • lease 自动续期不是过夜专属——long（1–2h）任务同样必须续期；只有 short 因预期单窗口完成而不续。
  • 不把 checkpoint repo 的 resume checkpoint 与 task-run epoch checkpoint 混成一个读取入口。
