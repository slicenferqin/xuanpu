Xuanpu Agent Runtime Plan

xuanpu-agent 长时间自主任务与上下文稳态迭代规划

本文梳理 150k 上下文预算、provider cache 命中、思维强度透传、长时间自主任务运行时之间的关系， 并给出后续从 turn-scoped request runner 演进到 task-run runtime 的分阶段计划。

日期：2026-06-04 分支：feat/xuanpu-agent-oh-my-pi 状态：迭代设计 范围：xuanpu-agent / XFP / Session HQ / usage analytics
评审批注（2026-06-04，对照 feat/xuanpu-agent-oh-my-pi 实际代码）： 以下章节内嵌的批注块即逐处回复。 属实 诊断已核实； 需修订 必须调整后再落地； 建议 优先级 / 措辞调整。 总评：诊断扎实、方向正确，主要缺陷是低估了现有 field_* 设施（把扩展写成新建）， 且重型 task-run 机制相对 ≤5 并发会话规模偏过度工程。

结论

当前问题不应被归结为“150k 是否足够”。150k 只适合作为单次 provider call 的上下文窗口上限。 长时间自主 agent 中，用户一句话可能触发一个持续几十分钟到数小时的任务运行， 这个任务会包含多个 epoch、多个 LLM call、多个工具调用和多个 checkpoint。

应废弃“单轮用户请求预算”这个硬上限语义，改成： 单次调用窗口 + epoch guardrail + task run policy + session steady state。

真正的稳态不是累计 tokens 不超过某个固定值，而是每一次 provider call 都能从玄圃持久化的任务状态中 重建一个小而准的当前上下文。累计 input 可以很高；当前上下文必须始终可控、可解释、可恢复。

当前现象与代码侧事实

现象 判断 影响
同一个 turn id 下出现多条 provider POST 一轮用户任务内部会多次调用 LLM，符合 agent loop 行为 不能把一次用户输入当成一次 LLM 请求来预算
多条请求 cache read 为 0 或命中不稳定 provider 看到的真实前缀每轮可能变化，且 provider session state 被禁用 长任务成本和延迟偏高，cache 指标无法稳定解释
UI / packet 显示 150k 当前更像单次 request 上限，却容易被理解成任务总预算 用户会误判 agent 无法长时间工作
思维强度未传到 provider 配置层和 model resolve 主路径缺少 reasoning effort / provider options UI 选择与真实 provider 调用不一致，任务表现不可控

关键实现点

  • src/main/services/xuanpu-agent/runtime.ts 当前每 turn 创建 fresh Agent， 并将 providerSessionState 置空。这保证玄圃拥有上下文真相，但牺牲 provider 侧会话延续。
  • src/main/services/xuanpu-agent-implementer.ts 的 anchor 会把完整 XFP packet 放在 provider 前缀中， 包含 packet id 和 volatile JSON。prefixHash 稳定不代表真实 provider prompt 前缀稳定。
  • src/main/services/xuanpu-agent/context/context-packer.ts 和 context/budget-manager.ts 仍以 80k / 150k / 200k profile 为主。
  • config-loader.ts 已解析 context.contextWindow 和 autoCompactTokenLimit，但主路径还没有把它们完整接到 packer、budget manager、snapshot 和 UI。
属实 评审 · 本节四条断言已逐条核实

四个「关键实现点」全部属实，诊断没有夸大： runtime.ts:448 确为 providerSessionState: undefined； 150_000 硬编码实际散落 4 处（budget-manager.ts:80、 context-packer.ts:92、harness/compiler.ts:201、implementer.ts:661）； config-loader.ts:246-257 确已解析 contextWindow/autoCompactTokenLimit 但主路径仍走常量。

尤其认同 anchor 失真这条：implementer.ts:547 注释自己写明 prefixSeed 只取 version+instruction，而真实发送的 anchor 含 JSON.stringify(compileResult.packet)（带 packetId/volatile JSON）。 「prefixHash 稳定 ≠ 真实前缀稳定」抓得很准，是本方案最有价值的诊断之一。

新的运行时模型

后续应把 xuanpu-agent 的核心单位从 turn-scoped request runner 升级为 task-run runtime。

Provider Call

单次 LLM 请求。只负责窗口、输出空间、tool schema overhead、provider 参数和 usage。

  • perCallContextWindow
  • maxOutputTokens
  • reasoningEffort
  • cacheRead/cacheWrite

Agent Epoch

长任务内部的短周期。用于 checkpoint、压缩、进展判断和防跑飞。

  • 若干 LLM calls
  • 若干 tool calls
  • 一个 checkpoint
  • 一个 next-step decision

Task Run

用户一句话触发的完整任务。可以持续很久，不应默认被低额度硬停。

  • 可续期 execution lease
  • 任务 ledger
  • 风险策略
  • 成本和进展可视化

Session Steady State

跨 epoch / turn / 重启的上下文稳态。目标是恢复能力，不是无限增长 prompt。

  • episodes
  • pinned facts
  • command traces
  • working set
用户请求
  -> Task Run
      -> Epoch 1: 诊断 / 读取 / checkpoint
          -> Provider Call 1..N
      -> Epoch 2: 修改 / 验证 / checkpoint
          -> Provider Call 1..N
      -> Epoch 3: 修复 / 总结 / checkpoint
          -> Provider Call 1..N
  -> 最终交付 / 可恢复状态

预算语义重定义

字段 作用 是否硬停 UI 呈现
perCallContextWindow 单次 provider call 最大上下文窗口 是 本次请求 14.6k / 150k
targetFillRatio 上下文稳态目标，例如 20%-40% 否 当前上下文健康度
softCompactRatio 触发 episode freeze / working set shrink 否 已触发主动压缩
epochGuardrail 检测工具风暴、重复失败、无进展循环 按原因 当前 epoch watchdog
taskRunPolicy 长时间自主任务策略：权限、成本、风险、lease 通常否 任务运行时长、成本、checkpoint
不建议默认设置“用户一句话最多 8 次 LLM / 10 分钟”。这会直接违背长时间自主 agent 的目标。 这些数字只适合用作短任务 profile 或 epoch-level watchdog。 
type ContextBudget = {
  perCallContextWindow: number
  targetFillRatio: number
  softCompactRatio: number
  emergencyCompactRatio: number
}

type EpochGuardrail = {
  checkpointEveryCalls: number
  checkpointEveryMs: number
  maxConsecutiveNoProgressCalls: number
  maxRepeatedToolCalls: number
  maxProviderFailures: number
}

type TaskRunPolicy = {
  autonomy: 'short' | 'long' | 'overnight'
  allowAutoLeaseRenewal: boolean
  costWarningThreshold?: number
  requireApprovalAboveCost?: number
  requireApprovalForRiskyWrites: boolean
}
属实 评审 · 语义重定义认同

「150k 是单次 call 上限、不是任务总预算」这个语义重定义正确且是本方案的核心认知价值。 配套的 per-call usage 记录方向也对——当前 agent_turn_usage_events（turn-repository.ts:327） 确实是 turn 聚合粒度，扩到每个内部 provider call 是合理的。

上下文稳态设计

稳态的核心目标是：不管任务跑了多久，每一次 provider call 都能看到足够的信息，同时不被历史噪声淹没。 这要求玄圃拥有一个 durable task state，而不是依赖 provider session 记忆。

稳定前缀与动态后缀

区域 内容 位置 缓存策略
Stable runtime policy 系统规则、工具使用原则、安全边界 最前 尽量跨 turn 不变
Stable task ledger 目标、约束、已完成项、当前阶段 靠前 只在 checkpoint 时更新
Relevant episodes 检索到的历史片段摘要 中段 按相关性进入，不整段重放
Working set 最近必要消息、文件片段、diff 摘要 中后段 持续去重、按 digest 管理
Live field packet 当前焦点、选择、git 状态、临时现场 靠后 高变内容不得污染稳定前缀
Current instruction 本次用户输入或 agent 下一步自我指令 最后 永不压缩

长任务 checkpoint

每个 epoch 完成后写入 checkpoint，checkpoint 是后续恢复和压缩的核心事实来源。

type TaskCheckpoint = {
  taskRunId: string
  epochId: string
  objective: string
  completed: string[]
  inProgress: string[]
  blockers: string[]
  touchedFiles: Array<{ path: string; digest?: string; summary: string }>
  commandTraceRefs: string[]
  testStatus?: string
  nextStep: string
  confidence: 'low' | 'medium' | 'high'
}
需修订 评审 · 本方案最重要的一条

这套稳态设计（task ledger / episodes / pinned facts / working set / checkpoint） 玄圃已经有对应的持久化设施，方案把「已有但未打通」写成了「从零新建」。现有表：

field_session_checkpoints ↔ TaskCheckpoint； field_pinned_facts ↔ pinned facts； field_episode_blocks / field_episodic_memory ↔ episodes； field_context_packages ↔ working set； field_memory_pages ↔ 长期记忆。

而且 implementer.ts 已有完整的 checkpoint resume 链路： verifyCheckpointForContext → resumedCheckpoint → buildAnchorSection / buildCurrentGoalFromCheckpoint。 上面「稳定前缀与动态后缀」那张表，几乎逐行对应现有 packContext 的分区逻辑。

建议：TaskCheckpoint 应表述为「在 field_session_checkpoints 上叠加 taskRunId/epochId 维度」，而非新结构。否则会和 field_* 形成两套并行真相， 违背 CLAUDE.md「Session Truth Sources：不要加第四个真相层」的约束。

Provider Cache 与可观测性

provider cache 不能被当作任务记忆，但应该被当作性能优化目标。当前问题在于： 玄圃虽然记录 prefixHash，但真实发给 provider 的前缀包含 volatile XFP packet， cache 命中自然不稳定。

  1. 把真正发送的前缀拆成 stable prefix 和 volatile suffix。
  2. 记录 actualPrefixHash，它必须来自真实 provider messages 的前 N tokens，而不是旁路 seed。
  3. 每次 cache miss 时记录 changed reason：模型变更、工具 schema 变更、stable policy 变更、episode 集合变更、volatile 字段误入。
  4. 同一个 task run 内展示 cache read/write 趋势，而不是只展示孤立 POST 行。
  5. 谨慎恢复 provider session state；它只能做 cache/latency 优化，不能成为上下文真相来源。

思维强度与 Provider 参数

xuanpu-agent 需要把 reasoning effort / thinking intensity 作为一等配置透传到 provider。 否则 UI、配置、真实调用之间会产生不可见偏差。 

type XuanpuAgentModelRef = {
  providerID: string
  modelID: string
  variant?: string
  reasoningEffort?: 'minimal' | 'low' | 'medium' | 'high'
  verbosity?: 'low' | 'medium' | 'high'
  providerOptions?: Record<string, unknown>
}
  • 配置 loader 需要校验 reasoning 字段。
  • model resolver 需要把 provider options 传给 pi-ai / stream function。
  • provider request snapshot hash 必须包含 reasoning 参数。
  • Session HQ / usage view 需要显示“实际传出的 reasoning effort”。
建议 评审 · 提前优先级

断言属实：model-config.ts:5-9 的 XuanpuAgentModelRef 确实只有 providerID/modelID/variant 三字段，reasoning 完全没透传。

但这是个用户当前可感知的正确性 bug（UI 选了高思维强度、真实调用却没带）， 不是增强。改动也小：扩 ModelRef 三字段 + resolver 透传 providerOptions + snapshot hash 纳入 reasoning。建议从迭代步骤的 P4 提到 P1 并行做，不必排在 task-run 架构之后。

建议 评审 · P0 / P2 优先级与范围

P0「rg no match 降级」与上下文稳态主题无关，是个独立 bug fix。 正确，但不该挤在这份架构方案里，建议单独拎成一条 issue。

P2 偏过度工程（对照记忆约束：实际并发活跃会话 ≤5、有人值守）。 execution lease + 自动续期是为「无人值守、规模化、过夜跑」设计的，单机 ≤5 会话基本用不上，建议降级或缓做。 三类 watchdog 有价值应保留，但 tool-storm 这条已有 StormDetector（runtime.ts:124），是复用而非新建。

建议把 P2 拆两层：① 必要核心 = epoch 划分 + 复用现有 watchdog + checkpoint 维度化； ② 可选重型 = lease / autonomy 审批，标注「仅在引入真正无人值守模式时再做」。 P5 的「跨重启恢复 task run」同理——有现成 checkpoint resume，是「接通」而非「新建」。

验收标准

  • 同一个长任务可运行多个 epoch，UI 能清楚展示 task run、epoch、provider call 的层级关系。
  • 150k 不再被呈现为用户请求总预算，而是单次 provider call 上限。
  • context.contextWindow 修改后能影响实际 packer、snapshot 和 context usage 事件。
  • 每个内部 provider call 都有独立 usage、cache、reasoning 参数记录。
  • stable prefix 的真实 hash 在无 schema / policy / ledger 变化时保持稳定。
  • 长任务累计 input 可以超过单次窗口很多倍，但当前上下文 fill ratio 保持在目标区间。
  • 连续无进展、重复工具调用、provider 首事件超时等异常能被 watchdog 明确归因。

非目标

  • 不通过简单提高 150k 到 500k 来掩盖上下文治理问题。
  • 不把 provider session 当作唯一记忆来源。
  • 不为了 cache 删除玄圃的现场感知能力。
  • 不把长时间自主任务默认限制在固定分钟数或固定 LLM 调用次数内。
