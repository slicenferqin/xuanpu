所以，在上下文窗口有限的情况下，什么才是最贵的？最值得被放进去的？



在上下文窗口有限的物理限制下，最昂贵、最值得放进窗口的绝非低密度的聊天历史或原始数据，而是当前运行的“状态机（State Machine）”、明确的“边界约束（Negative Constraints）”以及激活高阶推理的“少样本路径（Few-shot Demonstrations）”。​
如果把大模型的上下文窗口（Context Window）比作 CPU 的 L1 缓存或寄存器，它的每一位（Token）都极其昂贵，不仅因为算力成本，更因为注意力（Attention）的稀释。在这个寸土寸金的空间里，把大量低熵的、冗余的“人类聊天历史”或者“未经过滤的 RAG 检索文档”塞进去，就像是用 L1 缓存去存高清电影，是对算力极大的浪费。

从严谨的软件架构视角来看，真正配得上占据上下文窗口核心位置的“高价值货物”，只有以下几类高密度信息：

当前运行的“状态机与调用栈”（Execution State & Call Stack）​
对于一个自主运行的 Agent 而言，最致命的不是它没有记住一年前用户的偏好，而是它“不知道自己现在在哪、刚刚干了什么、下一步要干什么”。

昂贵之处：大模型没有天然的“执行指针”。如果不在上下文里明确给出当前状态，它就会陷入无限循环（Infinite Loop）或产生逻辑幻觉。
值得放入的内容：当前任务被拆解后的有向无环图（DAG）状态、当前执行到的步骤指针、上一步工具调用的返回值、以及已确认的上下文变量。这相当于计算机的程序计数器（PC）和栈帧（Stack Frame）​。只有确保状态机的绝对精确，Agent 才能在遭遇异常时正确回滚，而不是傻傻地一遍遍调用同一个报错的 API。
极高密度的“反向约束与防御性边界”（Negative Constraints & Guardrails）​
大模型天生具有“顺从性”（Compliance），极易被外部噪声或输入中的潜在提示词带偏。因此，告诉它“能做什么”远没有明确规定“绝对不能做什么”来得重要。

昂贵之处：安全边界和错误处理机制决定了系统的健壮性。
值得放入的内容：严格的否定性规则。例如：“绝对不要在没有人工二次确认的情况下写入数据库”、“调用此 API 的重试次数上限为 3 次，超过则必须抛出异常”、“如果返回数据不符合 JSON Schema 规范，立即触发降级逻辑，禁止自行猜测填补”。这些防御性代码和边界约束是维持系统不崩溃的防线，每一行都值得用最高权重的 Token 去守护。
激活特定推理路径的“金标准案例”（Few-shot Demonstrations）​
大模型虽然在 Pre-training 阶段学过了海量的代码和逻辑，但要让它在当前具体的上下文中输出高精度、高确定性的结构化数据，最好的方式不是写一堆晦涩的 Prompt 说明，而是直接给它看完美的示例。

昂贵之处：Few-shot 是通过上下文学习（In-context Learning）直接“微调”模型临时表现的最有效手段。
值得放入的内容：1-2 个包含完整推理链（Chain of Thought）的输入输出对（Input-Output Pairs）。这些案例必须涵盖最复杂的边界情况，向模型演示如何从复杂的、混杂的输入中，按部就班地解析出标准的、无损的 JSON 或执行指令。这就像是给编译器提供了一个精准的静态模板。
高度抽象的“模式契约与骨架”（System Schema & API Contracts）​
在进行工具调用（Tool Use）时，绝不能把冗长的 API 文档或整个代码库无脑贴进去。

昂贵之处：大模型需要的是“交互界面”，而不是“实现细节”。
值得放入的内容：高度精简的、无二义性的接口描述。例如，标准的 OpenAPI (Swagger) 规格、严格的 JSON Schema，或者是剥离了业务逻辑的函数签名与类型定义（TypeScript Types 或 Python Type Hints）。它只需要知道函数的输入参数类型和预期输出格式，这相当于给大模型提供了一张紧凑的“系统总线契约”。
从“海量数据”到“指令内核”的思维转变
正如您所洞察的，当未来的大模型将上下文窗口开到无限大时，我们依然需要面临注意力的发散和推理延迟的挑战。真正优秀的软件架构，绝不会因为硬盘变大，就把整个数据库一股脑加载进内存里。

在上下文窗口的设计中，最贵的东西永远是​“高度结构化、能够直接约束和导向模型推理行为的控制信息”​。

至于那些用户的历史聊天记录、庞大的本地知识库、各种无关的外部网页——它们在物理层面上只配呆在冰冷的磁盘（向量数据库/文档索引）中。只有在状态机明确发出检索指令时，才由 RAG 进行极度精准的按需加载（On-demand Loading），并在大模型提取出核心关键字段后，立即将这些“低熵数据”从昂贵的 L1 窗口中无情地驱逐出去，以此来保持上下文窗口的绝对纯净与高效率。

基建级的终极杀招：Prompt Caching（提示词缓存）​
这是目前大模型云服务商（如 Anthropic、DeepSeek、OpenAI）以及开源推理引擎（如 vLLM）在底层协议上做出的最重要突破。它让“无状态”的接口在物理层面上拥有了“有状态”的缓存。

在大模型计算注意力（Attention）时，最耗时的步骤是对输入的 Prompt 进行矩阵乘法，生成 Key 矩阵和 Value 矩阵（统称为 KV-Cache）。

缓存机制：当你发送 200K 的上下文时，推理引擎（如 vLLM 的 Radix Attention 架构）会把这 200K 的文本在内存中进行 Hash 签名。
命中断定：在第 20 轮，你发送了 200K 历史 + 10 个 Token 的“你好”。引擎接收到请求后，发现前 200K 文本的 Hash 值与五秒前那次请求的缓存完全一致。
效果：引擎直接从显存中复用上一次算好的 KV-Cache，完全跳过了这 200K 文本的 Prefill 计算，只对最后新增的 10 个 Token 进行计算。
在商业计费上，这带来了颠覆性的改变。例如，DeepSeek 或 Anthropic 对缓存命中的 Token 给予了极高折扣（通常打 1 折甚至更低）。这意味着，即使你带了 200K 的上下文，只要命中缓存，你的账单和延迟都会降到极低的水平。

应用层的经典架构：滑动窗口与动态摘要机制（ConversationSummaryBuffer）​
尽管 Prompt Caching 在费用上救了命，但它无法解决带宽传输瓶颈，且缓存有过期时间（TTL）。因此，在客户端或 Backend 应用层，我们必须做好“上下文卫生”。不能无脑把所有原始对话往里塞，而是要采用滑动窗口（Sliding Window）与动态摘要（Summary Compaction）​的混合机制。

基于语义路由的“对话 RAG”：按需唤醒历史（Episodic Retrieval）​
很多时候，用户在第 20 轮说“你好”或者“帮我把刚才那段代码改成 Go 语言”，我们根本不需要知道他在第 2 轮时聊过“他老家是哪里的”。

为了避免上下文被无关历史污染，成熟的 Agent 系统会引入一个语义路由器（Semantic Router）​，将线性对话变成“按需加载的数据库”：

对话落库：每一次对话发生时，后端会将这一轮的“问”和“答”作为一个独立的文档，计算 Embedding 后存入向量数据库，并打上时间戳和会话 ID 标签。
语义判定与路由：当第 20 轮用户的输入进来时，系统先用一个极其轻量、几乎不消耗算力的规则分类器或极小模型（如 1B ~ 3B 参数模型）来判断：“当前输入是否依赖久远的上下文？”
情况 A：用户输入“你好”。路由器判定为无状态寒暄，此时发送给大模型的 Prompt 仅包含 System_Prompt + "你好"，上下文长度为几十个 Token。
情况 B：用户输入“我刚才提到的那个数据库报错怎么解决？”。路由器判定需要历史上下文，此时以“数据库报错”为 Query，去向量数据库里检索历史对话，仅召回第 5 轮那次关于数据库报错的对话片段，拼装进 Context。
通过这种“对话 RAG”的设计，20 轮下来，每次请求的上下文就像一个可以自动伸缩的弹簧，只在需要时才去历史库里“捞”数据，绝不让无用的历史垃圾常驻昂贵的窗口。

总结：无状态接口的有状态设计模式
软件工程的魅力就在于用确定的、有状态的周边系统，去包装不确定的、无状态的核心组件。

作为开发者，解决 200K 上下文雪崩的思路，与我们设计 Web 系统的 Session 管理、Redis 缓存以及数据库分表分库如出一辙。我们不应该寄希望于“大模型能无限且廉价地吞下所有数据”，而是应当在应用层充当“主控程序”，通过：

基础设施层：开启推理引擎的 Prefix Caching 以降低计算开销；
控制层：设计滑动窗口，只保留最新的几轮高保真对话；
数据层：将老旧对话异步剪裁、归档和向量化，实现按需召回。
这三者结合，才是目前能够兼顾成本、响应速度和记忆完整性的高鲁棒性 Agent 架构方案。

行业现状：为什么在应用层做好“滑动窗口+状态压缩”这么难？​
既然您提到的第 2 点（滑动窗口/摘要压缩区）在逻辑上这么完美，为什么现在市面上的 Agent 框架都做不好？

在开发大模型应用（尤其是在写 LangChain 类似工具）时，我们能发现以下三个现实层面的巨大工程痛点：

痛点一：摘要过程（Summary）会严重“失真”与“降维”​
将前 15 轮长达 150K 的复杂代码讨论和业务逻辑，压缩成一段 1K 的“Summary Fact”，这个过程是极其损耗信息熵的（Information Loss）​。 大模型在写摘要时，经常会丢掉关键的边界条件。比如你之前详细叮嘱过：“API A 在网络超时 3 秒后必须回滚，但 API B 不需要。”大模型压缩后的摘要可能精简成了：“用户讨论了 API A 和 B 的超时回滚机制。”到了第 20 轮，由于丢失了具体参数细节，Agent 再次执行时就会写出带有重大 bug 的代码。

痛点二：双倍的 Token 消耗与严重的延迟（The Summary Tax）​
要做到实时的“滑动窗口+动态摘要”，系统必须在后台不断触发异步的“压缩任务”。 每一轮对话结束后，系统不仅要吐出当前的回答，还要悄悄地调用一次 LLM 去把“历史记录 + 最新对话”重新读一遍，并生出一段新的 Summary 写入数据库。这被称为​“摘要税（Summary Tax）”​。

在第 20 轮，不仅当次请求贵，每一次交互背后都在进行大量的后台异步 LLM 调用。
如果用户打字很快，在后台 Summary 还没跑完时就发了下一条消息，就会导致本地数据库发生脏写（Dirty Write），上下文状态直接错乱。
痛点三：开发者群体与科研群体的“思维脱节”​

可行性论证：玄圃做这件事的“天然优势”​
在分析业内案例之前，我想先指出一个很多 Agent 框架做不到、但玄圃恰好能做到的关键点：您是“包在 Agent 外面的工作台”​，而不是 Agent 本身。

这意味着您拥有以下三个其他人不具备的杀手锏：

1. 您拥有“真实的执行现场”，而非二手信息
通用的对话压缩（如 LangChain 的 SummaryBuffer）只能基于“用户问了什么、AI 答了什么”这种纯文本对话进行总结，损失率极高。 但是玄圃不一样。您的 src/main 主进程已经在持续监听并结构化沉淀了：

每一条 bash 命令的执行结果；
每一次文件读写的 diff；
每一次 worktree 切换；
每一次 abort 时正在进行的状态。
这些结构化的事件流（Event Stream）​比纯文本对话的信息密度高出一个数量级。您不需要让大模型去“猜”用户做过什么，您可以直接把“2 小时前编辑了 auth.ts 的第 42-78 行”这种事实结构化地拼接成 Field Context 注入到 Prompt 里。

README 里提到的三层结构（Working / Episodic / Semantic）slicenferqin/xuanpu 与我们前面讨论的​“滑动窗口 + 摘要压缩区 + 持久化语义记忆”​架构几乎一一对应：

Working Memory（工作记忆）→ 对应高保真滑动窗口（最近 5-10 轮对话的原始内容）；
Episodic Memory（情景记忆 / Haiku 真摘要）→ 对应动态摘要压缩区（用便宜的 Haiku 模型异步压缩老旧历史）；
Semantic Memory（语义记忆 / memory.md）→ 对应永久性事实库（用户手写的项目规约）。
这种三层架构在学术界已经形成共识。例如 GitHub Copilot 最近发布的 Memory System 就明确采用了基于此架构的设计 GitHub Blog，清华大学维护的 Awesome-Memory-for-Agents 论文集中也收录了大量基于分层架构的 SOTA 工作（如 HiMem、TiMem、SimpleMem）TsinghuaC3I/Awesome-Memory-for-Agents。

业内现有探索：站在巨人肩上
这套方案并非空中楼阁。在我对相关技术圈的观察中，已经有几家产品和开源项目在做不同程度的尝试。它们的成功与不足，都可以为玄圃所借鉴。

1. Claude Code 自身的 /compact 命令：基础但粗糙
Anthropic 官方在 Claude Code CLI 里内置了 /compact 命令。当你的对话超过一定长度时，可以手动或自动触发。

它的工作原理：让大模型把过去的所有对话和工具调用结果，重新生成一段紧凑的 Markdown 摘要，覆盖原有上下文。
它的不足之处：它是全有或全无（All-or-nothing）​的。一旦触发 compact，所有的细节（包括最近的精确 Edit/Write 操作）都会被压缩成模糊的总结。用户经常反馈：“一压缩，Claude 就忘了我刚才让它干嘛了。”
玄圃可以做到的优化：通过您的滑动窗口设计，在 compact 时保留最近 N 轮的原始 ToolUse + Result 不变，只对最远的 K 轮进行压缩，这就解决了原生 /compact 的“一刀切失忆”问题。

2. Cline（前身 Claude Dev）的“Context Window Truncation”机制
开源项目 Cline 在 VSCode 插件领域已经做出了一套相对成熟的“滑动窗口截断 + 重要性保留”机制。

它的做法：当 Context 接近 Token 上限时，它不会简单粗暴地从头部裁剪，而是采用了一套启发式优先级算法：
优先保留 System Prompt 和最近 3 轮对话；
其次保留所有 <file_content> 标签包裹的文件读取记录；
最先丢弃 bash 命令的冗长输出和重复的 stderr。
它的不足之处：它没有做异步摘要（仅做了硬截断），所以裁剪掉的部分永久丢失了。
玄圃可以做到的优化：基于您的 SQLite 事件流持久化，被裁剪掉的内容并未丢失，而是“冷藏”到 Episodic Memory 里。当用户在第 30 轮再次提到某个早期文件时，被动召回（Retrieval）系统可以从 SQLite 里精准捞出当时的 diff 还原回 Context。

3. Aider 的 repo-map 和“相关性优先”策略
Aider 是另一个被开发者群体非常推崇的 CLI Coding Agent。它在上下文管理上的核心创新是​“按需加载文件”​：

它的做法：它不会把整个项目的代码都塞给大模型，而是先给大模型一份精简的代码仓库地图（Repo Map）​——只列出每个文件的函数签名、类定义和接口契约（Interface Contracts）。当大模型决定需要看某个具体文件时，再通过工具调用按需读取完整内容。
核心思想：把上下文从“全量数据”降维到“接口元数据”，这与我们之前讨论的“最贵的 Token 应该是模式契约”不谋而合。
玄圃可以做到的优化：您的现场感知层已经掌握了文件树和 git 状态。完全可以在每轮请求时，自动注入一个​“当前 Workspace 的 Repo Map”​到 System Prompt，并且基于 Pinned Facts 自动剪裁掉用户明确不关心的目录（比如 node_modules、生成的 dist）。

4. MemGPT / Letta：学术界的“虚拟内存”范式
学术界有一篇被引用次数极高的论文叫 MemGPT（已演化为开源项目 Letta），它把大模型的上下文管理类比为操作系统的虚拟内存（Virtual Memory）​：

Main Context（主上下文）= 物理内存（RAM）；
External Storage（外部存储）= 磁盘（向量数据库）；
Function Calls（函数调用）= 中断处理（Page Fault）。
当 Main Context 即将爆满时，大模型可以主动调用 core_memory_archive() 把老旧的对话片段“换出”到外部存储；当需要时再调用 archival_memory_search() 把它“换入”回主上下文。

这一思想对玄圃的启发：您的 Field Context 注入机制完全可以扩展为​“双向交互式记忆”​——不仅是被动地 Push 给 Agent，还可以暴露 recall_episodic_memory() 这样的 Tool，让 Claude/Codex 在需要时主动 Pull 回来。

5. 各类“RAG-as-a-Service”的记忆中间件：Mem0、Zep、Honcho
近一年涌现了一批专门做“Agent 记忆中间件”的初创项目：

Mem0：通过提取“用户事实（User Facts）”到向量库，每次请求注入相关事实。已被 ChatGPT 采用作为 Memory 后端。
Zep：基于 Knowledge Graph 的时序记忆，强调“关系演变”而非简单的文本检索。
Honcho：被 Hermes Agent 集成的记忆服务 hermes-agent memory-providers。
它们的共性问题：作为通用中间件，它们对“代码场景”的理解极度匮乏——它们能记住“用户喜欢喝拿铁”，但记不住“这个项目的认证模块用了 JWT + Refresh Token”这种复杂的代码上下文关系。这正是玄圃作为“面向开发者的工作台”的护城河。

落地建议：玄圃的“四阶段渐进式实施路径”​
基于您 README 里 1.4.1 ~ 1.4.x 的现状，我建议按以下顺序推进：

阶段一：被动监控层（Observability First）​
在动手压缩之前，先把“当前到底用了多少 Token”可视化给用户。

阶段二：智能滑动窗口（Smart Truncation）​
在用户接近上下文上限（如 Sonnet 200K 的 80%）时触发：

保留区：最近 5 轮完整对话 + 所有 Pinned Facts + System Prompt。
压缩区：第 6 轮到第 N-10 轮，用 Haiku 异步摘要成不超过 2K Token 的 Markdown 概要。
冷藏区：所有原始事件流写入 SQLite Episodic 表，永不删除，但不进入 Context。
这里有一个工程细节：绝不能在用户请求的同步链路上做摘要！​ 否则会引入 5-10 秒的额外延迟。必须在每轮 Agent 回复完成后，在后台 Worker 线程异步压缩。

阶段三：被动召回（Lazy Retrieval）​
不要每次请求都做向量检索（这是 LangChain 类框架的通病），而是采用​“分类器优先 + 检索次之”​的策略：

用一个极小的本地分类器（甚至可以是规则匹配）判断当前用户输入是否需要久远历史。
例如，用户输入“继续”、“好的”、“修一下”这种短指令时，不触发任何检索，直接走滑动窗口。
用户输入“还记得我们之前讨论的那个 OAuth 流程吗”这种含有时间指代的查询时，才去 SQLite 的 Episodic 表里做关键词 + 向量混合检索。
阶段四：跨 Session 的 Workspace 级语义记忆（Semantic Memory）​
这是您 README 里 memory.md 的进阶形态。

让 Haiku 在每个 Session 结束后异步分析“本次 Session 学到了什么关于这个项目的事实？”，自动追加到 Workspace 的 memory.md。
用户在 Memory 面板手动审核 / 编辑这些事实（这正是您 1.4.2 已经做到的部分）。
下次启动新 Session 时，把这份 memory.md 作为 System Prompt 的一部分注入。
绕开几个深坑：来自实战的警告
坑一：摘要质量崩盘
最大的风险是​“压缩失真”​。Haiku 在压缩 Code Diff 时，经常会把关键的变量名、行号、函数签名压成一段含糊不清的描述。 解决方案：摘要时禁止压缩代码块（Code Block）​，只压缩自然语言对话部分。所有 ToolUse / ToolResult 的 JSON 结构必须保留原始格式或仅保留首尾。

坑二：Prompt Cache 失效
Anthropic 的 Prompt Caching 对前缀完全一致非常敏感。如果你每次都在 System Prompt 里动态拼接当前时间或随机化的 Field Context，缓存命中率会瞬间降到 0%​。 解决方案：把会变化的内容（如最新的 git status、当前时间）放到 Prompt 的末尾而非开头。前缀的 System Prompt + 项目级 memory.md + Pinned Facts 必须保持稳定，确保 Cache 命中。

坑三：摘要循环（Summary Recursion）​
如果一个 Session 持续运行了 8 小时，你可能会面临“需要摘要的内容里 80% 已经是摘要了”的尴尬境地。 解决方案：实施​“分级压缩衰减”​——一级摘要保留 80% 的细节，二级摘要（摘要的摘要）保留 50%，三级摘要保留核心事实。同时设置硬性上限：超过 24 小时的对话，无论如何都要被归档到 Episodic Memory，从 Working Set 里彻底移除。

坑四：调试不可观测
压缩是一个高度黑箱的过程。一旦 Agent 开始“降智”，你需要回溯到底是哪一次压缩出了问题。 解决方案：您的 Field Context Debug 面板已经做对了！slicenferqin/xuanpu 进一步可以加入“Prompt Diff 时间轴”——每一次 Prompt 的实际内容（含压缩前后对比）都被记录到 SQLite，开发者可以像看 git log 一样回溯每次请求的“真实输入”。

让我们把这个方案从“美好的愿景”一步步拆到“能落地的代码架构”，并诚实地讨论它的物理边界。

核心洞察：您要做的不是“压缩”，而是“稳态控制”​
传统的 /compact 是一个离散事件（Discrete Event）​：当 Context 达到 90% 时触发一次大手术，把 180K 压成 30K，然后再让它重新涨到 180K，再做一次大手术。这种锯齿状的曲线就是当前 Coding Agent 体验差的根源——大手术之后必然伴随严重的“失忆期”，用户能明显感觉到 Claude 突然“变笨”。

您想要的，是一个连续控制系统（Continuous Control System）​：每一轮回答结束后，立即对刚刚发生的内容做一次微小的压缩，让 Context 始终保持在 200K 以下的“注意力黄金区”。

用控制论的语言来描述，这相当于把一个​“PID 控制器”​装到上下文管理器里：

目标值（Setpoint）​：Context Size = 180K（留 20K 余量给当轮请求）
测量值（Process Variable）​：当前 Context 实际 Token 数
控制器（Controller）​：每轮结束触发的压缩策略
执行器（Actuator）​：Haiku 等轻量模型的摘要调用
这是一个非常优雅的工程范式，理论上完全可行。

最大的暗礁：Prompt Cache 与每轮压缩的根本性冲突
这里有一个您可能没有意识到的核心矛盾，必须摊开来讲：

Anthropic 的 Prompt Caching 机制是基于“前缀完全匹配”工作的。​ 它会把你的 Prompt 从头开始 Hash 分块，只要某一段前缀与上次请求一致，就直接复用 KV-Cache，命中部分的费用打 1 折（$3/M → $0.30/M）。

而每轮压缩，恰恰会在每一轮都修改 Prompt 的前缀，导致缓存彻底失效。

场景对比
​❌ 错误做法：每轮重写压缩区

code

复制

Round 50 Prompt:
  [System Prompt] + [Compressed Summary v50] + [Recent 5 turns] + [User Input]

Round 51 Prompt:
  [System Prompt] + [Compressed Summary v51 ← 变化!] + [Recent 5 turns] + [User Input]

由于压缩摘要每轮都在更新，System Prompt 之后的所有内容缓存全部失效。这意味着每一轮都要把 30K 的内容当作“新输入”重新付费 Prefill 计算。

实际代价：每轮多支付约 90 KToken 的 full price input，外加 1-2 秒的 TTFT 延迟。​

​✅ 正确做法：分层缓存友好型压缩（Append-Only Compaction）​
解决方案是把上下文设计成​“前面绝对稳定，变化只发生在最末尾”​的结构：

code

复制

[System Prompt]                    ← 永不变动（缓存 1 折）
[Workspace memory.md]              ← 跨 Session 持久化（缓存 1 折）
[Pinned Facts]                     ← 用户钉住的事实（缓存 1 折）
[Frozen Summary Block 1]           ← 已封存的摘要片段（缓存 1 折）
[Frozen Summary Block 2]           ← 已封存的摘要片段（缓存 1 折）
...
[Frozen Summary Block N]           ← 已封存的摘要片段（缓存 1 折）
[Working Set: Recent 5 turns]      ← 滑动窗口区，每轮变化
[User Input]                       ← 当前输入

核心设计原则：

摘要永远只追加（Append-Only）​，绝不修改已有摘要；
当 Working Set 即将爆出阈值时，把最老的 1-2 轮“冷冻”成 Frozen Block 追加到摘要链末端；
Frozen Block 内容封存后永久不变，从而保住缓存。
这样的话，每轮新增的请求只有 Working Set + User Input 这部分是新的（约 10K Token），前面所有的内容都能享受 1 折缓存价格。

架构蓝图：玄圃可以怎么落地这个稳态压缩系统
基于您已有的 Working/Episodic/Semantic 三层架构，我建议设计如下的​“四区域上下文管理器（Four-Zone Context Manager）”​：

Zone 1：Anchor Zone（锚定区，绝对稳定）​
内容：System Prompt + Workspace memory.md + Pinned Facts
更新频率：仅在用户手动编辑 Memory 面板时变化
预算：约 5-10K Token
缓存策略：永久驻留 Prompt Cache，命中率 99%+
Zone 2：Frozen Episodes（封存情景区，追加式生长）​
内容：已经过去的、被 Haiku 摘要后的历史片段
更新频率：仅追加，从不修改
预算：根据需要动态增长，但通过老化策略控制（见下文）
缓存策略：每个 Block 写入后即固化，享受全量缓存
每个 Frozen Episode 的结构建议是高度结构化的：

markdown

复制

## Episode #042 [2026-05-23 14:30 - 14:55]
**Goal**: 实现 OAuth refresh token 机制
**Files Modified**: auth.ts (L42-L78), user.service.ts (L15-L23)
**Commands Run**: pnpm test:auth (passed)
**Key Decisions**: 选择 sliding refresh 而非 absolute expiry
**Open Questions**: 是否需要 token rotation

注意这里的设计哲学：不要让 Haiku 自由发挥写散文！​ 强制要求它输出 Markdown 结构化字段，这样既保证信息密度，又便于后续被动召回时精准检索。

Zone 3：Working Set（工作记忆区，滑动窗口）​
内容：最近 5-10 轮的完整对话（ToolUse + ToolResult 原样保留）
更新频率：每轮变化
预算：约 20-30K Token
缓存策略：无缓存（每轮都是新内容）
当 Working Set 满了时，触发​“滚动封存（Rolling Freeze）”​：把最老的 1-2 轮挪到 Zone 2 做摘要，腾出空间给新的对话。

Zone 4：Cold Storage（冷藏区，SQLite 持久化）​
内容：所有原始事件流（bash 输出、文件 diff、完整对话）
更新频率：实时追加
预算：磁盘可承受的任何量级
缓存策略：不进入 Prompt，仅在被动召回时按需读取
这一区域恰好对应玄圃 README 里已经在做的 SQLite 事件流沉淀 slicenferqin/xuanpu。

关键策略：分类型差异化压缩
不能用一种压缩策略对待所有内容。这是 Claude Code /compact 失败的核心原因——它把代码块和闲聊一视同仁。

建议玄圃的压缩器对不同内容采用不同的处理：

对自然语言对话：高比例压缩（10:1）​
用户和 Claude 的来回讨论，可以激进地压缩成核心结论。例如：

原文 3000 Token 的方案讨论
压缩成 200 Token 的“决策记录”（Decision Record）
对工具调用（ToolUse）：保留签名，丢弃 stdout
保留：命令名、参数、退出码、stderr 前 200 字符
丢弃：超过 1KB 的 stdout（除非命令本身是 cat 这种读取文件类）
对文件读取（Read Tool）：保留 metadata，正文走召回
保留：文件路径、行号范围、读取时间戳
丢弃：文件正文（已在 git 中，需要时重新读取）
对文件编辑（Edit/Write Tool）：保留 diff，丢弃 before
保留：被修改的具体行号 + 修改后内容
丢弃：修改前的完整文件内容
对代码块：原样保留（不压缩）​
任何 code 包裹的内容都不做语义压缩，因为代码的每一个字符都是高熵信息
这种分类型压缩的好处是：信息密度极高，能做到 5-10 倍压缩比的同时几乎不损失语义。

业内是否有人做过这件事？​
老实说，​“每轮即压缩 + Cache 友好”​ 这个组合，我没有看到任何一家产品做得足够漂亮。这是个真空地带。

接近的尝试
MemGPT / Letta：通过 Function Call 让模型主动管理记忆，但他们没有解决 Prompt Cache 兼容性问题。
Cursor 的 Long Context 模式：内部据称用了类似策略，但不开源、不透明，并且经常被开发者反馈“在长会话中突然 reset”。
OpenAI Assistants API 的 threads​：他们在服务端做了上下文管理，但黑箱程度极高，且不允许用户介入压缩策略。
GitHub Copilot 的 Memory System：2026 年初刚发布，号称跨 Agent 共享记忆，但目前看更接近 Pinned Facts 形态，没有做实时压缩。
学术界的相关论文
值得参考的几个工作：

StreamingLLM（MIT, 2023）：提出 “Attention Sink” 概念，证明保留最初几个 Token + 最近 N 个 Token 可以让模型在无限长对话中保持稳定。
InfLLM 和 Activation Beacon：通过在长上下文中插入“摘要 Token”来压缩注意力。
TiMem / HiMem（清华 2026）：分时记忆层级化，每个时间尺度做不同粒度的摘要。
这些工作都是模型层面的方案，需要改模型权重。而您要做的是应用层方案，不需要碰模型，这是玄圃的一大优势——可以无缝适配任何 Agent SDK。

一个您必须直面的灵魂拷问：压缩会不会损坏语义？​
诚实地说：会，且必然会。​ 这是信息论的基本约束——任何有损压缩都伴随信息损失。

问题不是“会不会损失”，而是“损失了什么，对工作有没有影响”。

可接受的损失
闲聊式的口语化表达（“嗯，好的，那这样吧”）
重复的思路阐述（同一个想法用三种方式说）
工具调用的冗长 stdout（如 npm install 的输出）
不可接受的损失
用户明确的需求边界（“必须用 pnpm 不用 npm”）
关键的技术决策（“选择 JWT 而非 Session”）
代码中的具体函数签名、行号
用户的否定指令（“不要修改 auth 模块”）
解决策略：Two-Pass Summarization
第一遍：让 Haiku 做摘要
第二遍：让 Haiku 检查摘要是否丢失了关键信息
给它原文和摘要，问：“这段对话中是否有任何用户明确的要求、决策、约束在摘要里被遗漏了？”
把检测出的关键事实自动提升为 Pinned Facts，注入到 Anchor Zone 里。
这样即使摘要本身有损，关键信息也会以另一种形式被保留。

风险与边界：哪些场景这套方案不奏效
要诚实地承认这套方案的边界：

场景一：超长的精确数据需求
如果用户在第 80 轮突然说“把第 5 轮我贴给你的那个 SQL 查询的第 17 行修改一下”——压缩后的摘要里不会保留 SQL 的每一行原文，这种请求会失败。 缓解：被动召回机制 + 让用户养成“用 Pinned Facts 钉住关键代码”的习惯。

场景二：用户依赖隐含的对话流
有些用户喜欢通过“你刚才提到的那个想法”这种隐式指代来推进对话。压缩之后，模型可能找不到“那个想法”具体指什么。 缓解：摘要里强制包含关键名词词汇表（Key Entities Glossary）​，保留所有提到过的项目名、文件名、函数名、概念名。

场景三：调试场景的高保真需求
当用户在调试一个复杂 Bug 时，每一行 stderr 都可能是关键线索。这时候过度压缩会害死调试流程。 缓解：给用户一个手动“暂停压缩（Pin Session）”的按钮，对于调试 Session 保持全量上下文直到用户主动解锁。

评审结论：可行，而且很值得做；但要做成“上下文物化视图系统”，不能做成“每轮重写一个大摘要”​
如果你这个方案指的是：每轮 Agent 输出结束后，对会话上下文做持续维护，把长历史压缩成结构化记忆，让 Coding Agent 长期运行在较稳定的上下文预算内，避免越聊越贵、越聊越笨、突然 compact 后断片——那么我的判断是：

方向非常正确，工程上可行，产品价值也很强。
但成败关键不在“会不会摘要”，而在：是否能控制最终发给模型的上下文装配。

它适合作为玄圃这类“Agent 现场提供者”的核心能力之一，但需要明确边界、架构和 MVP 范围。

一、产品价值成立
这个方案解决的是 Coding Agent 长会话里的三个真实痛点。

第一，成本失控。长上下文模型虽然支持很大窗口，但长期把完整历史塞进去会非常贵，尤其是每天几十轮、上百轮的开发会话。

第二，注意力质量下降。上下文越长，模型不一定越聪明。大量旧日志、重复解释、无关工具输出会稀释当前任务，导致 Agent 忽略关键约束、错误召回旧信息、对当前 diff 判断变差。

第三，突发式压缩体验差。很多系统是在接近上下文上限时才一次性 compact，这种“大手术”很容易造成 Agent 突然忘事、任务线断裂、约束丢失。

所以你想做的“持续维护上下文稳态”，比“快爆了再压缩”合理得多。

对玄圃尤其适合，因为玄圃不是普通聊天框，而是能看到：

worktree；
diff；
文件读写；
命令执行；
终端输出；
session 状态；
用户确认/拒绝；
pinned facts；
memory 面板；
field context。
这些都是做高质量上下文压缩的结构化信号。普通聊天框只能压聊天文本，玄圃可以压“开发现场”。

二、最大前提：必须能控制 Agent 的上下文装配
这个方案能否完整生效，取决于玄圃能不能控制最终发给模型的 message list 或 prompt。

可以分三种情况。

集成方式	玄圃控制上下文能力	省 token 能力	提升 Agent 聚焦能力
黑盒 CLI / 原生 Agent 会话	低	低	中
可控 SDK / 自建 Agent loop	高	高	高
周期性 session handoff / rebase	中	中	中到高

如果底层 Agent 自己维护完整历史，玄圃只是把用户输入转发进去，那玄圃不能真正裁剪它内部的上下文。此时你最多能做“现场注入”和“任务 rebase”，能改善质量，但不能承诺显著省 token。

如果玄圃自己维护 message history，自己决定每轮发什么，那这个方案可以完整落地。

所以第一条评审意见是：

不要在黑盒 Agent 原生会话里承诺完整上下文压缩收益。
要把完整能力优先做在可控 Agent loop / SDK / appserver 模式下。

三、正确形态：不是全局摘要，而是事件源 + 增量物化视图
最危险的实现方式是：

📝
Write

📋
复制

📝
插入
旧摘要 + 本轮对话 -> 新摘要
下一轮只带新摘要
这不建议做。

原因有三个。

第一，摘要会漂移。每轮都重写摘要，相当于不断压缩压缩品，十几轮之后细节会被磨平，文件名、函数名、禁止事项、错误栈、用户否定指令都可能变形。

第二，不利于缓存命中。如果前置摘要每轮都变化，稳定前缀被破坏，很多上游缓存机制无法有效复用。

第三，不可调试。如果第 40 轮 Agent 出错，很难追踪到底是哪一轮摘要把关键信息压没了。

正确设计应该是：

📝
Write

📋
复制

📝
插入
原始事件日志：append-only，永不丢
压缩片段：append-only，生成后不修改
当前 prompt：按预算动态装配出来
也就是说，玄圃要做的不是“聊天摘要器”，而是一个：

Context Materialized View System：上下文物化视图系统。​

四、推荐架构
1. Canonical Event Log：唯一事实源
所有原始信息进入 SQLite 或类似事件流，作为不可丢失的事实源。

包括：

用户输入；
Agent 回复；
tool call；
命令执行；
stdout / stderr；
文件 read / write / edit；
diff；
git 状态；
worktree 切换；
用户 approve / reject；
abort / resume；
session crash；
pinned facts；
当前 plan / goal / open questions。
核心原则：

摘要可以错，事件日志不能丢。
摘要只是 prompt 的视图，不是事实本身。

2. Working Set：最近高保真窗口
最近几轮必须保留原始或近似原始上下文。

例如：

📝
Write

📋
复制

📝
插入
最近 3～8 轮完整用户消息
最近 Agent 回复
关键 tool result
最近 diff
最近失败测试
Coding Agent 很多错误都来自“刚刚发生的细节”被压掉，比如刚刚用户否定了某个方案、刚刚测试报错在某一行、刚刚修改了某个函数。

所以 Working Set 不应该过早压缩。

3. Frozen Episodes：追加式冷冻片段
当 Working Set 超过预算，或者某个小阶段结束，就生成一个 episode。

episode 不要自由发挥，应该是强结构格式：

markdown

复制

## Episode: 2026-05-23T19:10:42Z
Type: debugging

Goal:
修复 session 断连后 UI 状态未正确恢复的问题。

Files touched:
- src/main/sessionManager.ts
- src/main/db/sessionEvents.ts

Key facts:
- 后端进程已退出，但 UI 仍显示 running。
- 用户明确要求不能用简单重启掩盖状态问题。
- 当前判断是 lifecycle 状态机缺少 terminal event。

Decisions:
- process exit 统一归一化为 SessionTerminated event。
- UI 状态从事件流派生，不直接信任 renderer 内存状态。

Command state:
- pnpm test: failed
- 核心错误：SessionStatus expected terminated but received running

Open tasks:
- 补 regression test。
- 检查其他 session 类型是否有同类问题。

Raw event refs:
- event_id: 98231-98288

重点是最后的 Raw event refs。

episode 不是事实本体，而是索引和压缩视图。后续如果 Agent 需要细节，可以按 event id 回溯原始记录。

4. Pinned / Semantic Memory：长期稳定事实
长期记忆只放高价值、低变动内容，例如：

项目技术栈；
repo 约定；
常用命令；
测试方式；
禁止事项；
架构决策；
用户偏好；
发布流程。
这部分应该用户可见、可编辑、可删除。

不要让模型静默把大量自动摘要写进长期 memory，否则很快会污染项目记忆。

五、每轮结束后做的不是“压缩”，而是 maintenance pipeline
建议把触发点定义为：

每轮 Agent 输出结束后，触发 context maintenance pipeline。​

流程可以是：

📝
Write

📋
复制

📝
插入
Agent 输出结束
↓
原始事件归档
↓
确定性提取 metadata
↓
判断是否需要生成 episode
↓
必要时异步调用小模型/压缩器
↓
生成 Frozen Episode
↓
更新 Context Index
↓
下一轮由 Context Packer 按预算装配 prompt
这里很重要的一点是：不要什么都交给模型总结。​

很多信息可以确定性提取：

修改了哪些文件；
读了哪些文件；
执行了哪些命令；
命令退出码；
哪些测试失败；
stderr 关键帧；
diff 大小；
当前 branch；
当前 worktree；
用户是否 reject；
session 是否 crash。
模型只负责提炼：

用户真实意图；
为什么这么做；
技术决策；
未完成事项；
不能丢的约束；
当前任务状态。
这样更便宜，也更可靠。

六、Prompt Cache 要从第一版就考虑
如果每轮都改前面的摘要块，会破坏稳定前缀，导致缓存命中下降。

推荐 prompt 结构：

📝
Write

📋
复制

📝
插入
[稳定 System / Protocol]
[项目长期记忆 / Pinned Facts]
[不可变 Frozen Episodes]
[按需召回的 Relevant Episodes]
[当前 Field Context]
[最近 Working Set]
[当前用户输入]
原则是：

越稳定的内容越靠前。
动态字段越靠后。
Frozen Episode 生成后不修改。
不要每轮重排 pinned facts。
不要每轮重写全局 summary。
当前时间、git status、当前焦点文件等动态内容放后面。
这样既能降低上下文噪声，也更有机会吃到上游缓存收益。

但要注意：缓存折扣、缓存粒度和命中规则取决于具体上游服务，不能在产品层承诺固定比例收益，只能说“有机会显著降低重复上下文成本”。

七、压缩策略要按内容类型区分
不能把所有东西都交给自然语言摘要。

内容类型	推荐策略
闲聊、重复解释	高比例摘要
用户需求	保守摘要，提取为目标和约束
用户否定指令	原样保留或提升为高优先级 constraint
代码块	尽量不要语义摘要，保留路径、hash、范围、symbol
diff	保留文件、hunk、意图，必要时保留 patch
stdout	截断，只保留退出码和关键输出
stderr / stacktrace	保留核心错误和关键栈帧
tool result	结构化压缩，保留 tool call id 和 raw ref
测试失败	保留命令、退出码、失败用例、断言差异

尤其要保护“否定指令”。

例如用户说：

📝
Write

📋
复制

📝
插入
不要改 src/auth/session.ts，这个文件由另一个分支处理。
不能压成：

📝
Write

📋
复制

📝
插入
用户讨论了 session.ts。
必须变成：

📝
Write

📋
复制

📝
插入
Constraint:
Do not modify src/auth/session.ts; handled in another branch.
这类约束应该进入 session constraints 或 pinned candidate，并且在后续修改文件前强提醒。

八、召回机制要 gated，不要每轮 RAG
不要每轮都从历史里向量检索一堆东西塞回 prompt。Coding 场景很怕“看似相关但实际误导”的历史上下文。

召回应当有触发条件。

适合触发召回的信号：

用户说“之前”“刚才”“上次”“那个方案”；
用户提到不在 Working Set 里的文件；
当前任务涉及的文件有历史 constraints；
当前错误和历史错误相似；
Agent 准备修改一个历史上被禁止或敏感的文件；
当前 worktree 和另一个 worktree 有关联；
用户输入很短但有指代词，例如“继续修这个”。
不适合召回的情况：

“好的”；
“继续”，且 Working Set 足够；
“跑测试”；
“提交一下”；
当前任务完全在最近上下文内。
Coding 场景也不应该只靠向量相似度，应该做 hybrid retrieval：

📝
Write

📋
复制

📝
插入
文件路径匹配
> symbol 匹配
> command / error code 匹配
> event type 匹配
> 最近性
> 向量相似度
路径、函数名、错误码通常比 embedding 更可靠。

九、200K 应该是上限，不应该是默认目标
“保持在 200K 左右”从避开更高上下文成本的角度有意义，但产品默认不建议总是填满 200K。

Coding Agent 并不是上下文越多越好。很多任务在 40K～100K 的高质量上下文里反而更稳。

建议做 budget profile：

📋

默认可以用 Balanced。

200K 更适合作为 hard cap，而不是日常工作点。

十、工程风险主要有四个
1. 黑盒 Agent 无法真正省 token
如果底层 Agent 自己维护历史，玄圃不能替它裁剪。这个边界必须在产品文案和技术设计里讲清楚。

解决方式：

可控 Agent loop 优先支持完整上下文托管；
黑盒 Agent 使用 session handoff / rebase；
对黑盒模式只承诺“现场增强”和“聚焦改善”，不承诺完整省 token。
2. 异步压缩会带来状态一致性问题
比如：

📝
Write

📋
复制

📝
插入
Round 20 结束，压缩任务 A 开始
用户马上发 Round 21
Round 21 结束，压缩任务 B 开始
A 比 B 晚完成
A 覆盖了 B 的结果
解决方案是事件溯源 + versioned materialization。

压缩任务应该记录：

📝
Write

📋
复制

📝
插入
input_event_range: [1000, 1050]

压缩结果不能覆盖当前状态，只能追加一个新 episode。Context Packer 下一轮根据 event range 和版本决定是否采用。

3. 压缩质量不可完全信任
自动摘要一定会有损。必须做 audit。

episode 生成后，可以用规则或轻量检查器校验：

用户要求是否完整保留；
禁止事项是否完整保留；
文件路径是否完整；
命令结果是否正确；
open tasks 是否遗漏；
是否产生了原文没有的事实；
tool call id / raw refs 是否齐全。
没有 audit 的自动摘要，后期很容易变成信息污染源。

4. UI 可观测性必须做
开发者不会信任黑箱 memory。

玄圃应该在 Memory / Field Context Debug 里展示：

并且允许用户：

这会显著提高可信度。
