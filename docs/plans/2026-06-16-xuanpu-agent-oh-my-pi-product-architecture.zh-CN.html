Xuanpu Agent · Productized Runtime Architecture

xuanpu-agent 基于 oh-my-pi 打造的产品化架构方案

本文重新调研 oh-my-pi 上游、当前分支代码和既有 xuanpu-agent 设计文档后，给出新的产品化路线： xuanpu-agent 应该基于 oh-my-pi 的 agent/runtime/tool/session 能力继续打造，而不是把 oh-my-pi 当作一个浅层 adapter。推荐路径是“可控 fork-core + Xuanpu 上下文内核 + 独立发行面”，避免从零造 agent， 也避免把整个上游产品无边界硬拷进桌面端。

日期：2026-06-16 分支：feat/xuanpu-agent-oh-my-pi 状态：方案文档 / 可实施设计 基线：@oh-my-pi 15.2.4，本地 @xuanpu/pi-agent-core shim 上游最新：v16.0.1 / 2026-06-15

0. 结论先行

新路线不是“给 oh-my-pi 写一个 Xuanpu adapter”，而是把 xuanpu-agent 定义为一个 oh-my-pi-derived product runtime：复用并持续跟进 oh-my-pi 的 agent loop、 provider、tool harness、compaction/session 经验和 CLI/SDK 基础，同时由 Xuanpu 拥有最终的 TaskRun、UserRound、ContextSegment、现场协议、上下文预算、工具/媒体卸载、记忆、审计和桌面集成。

推荐决策：采用“产品化 fork-core”路线。当前 @xuanpu/pi-agent-core 只是薄 re-export + runTurn() 修补，下一阶段应升级为 可控的源代码 fork/patch layer：保留上游同步边界，沉淀 Xuanpu 专属 API，不再把 oh-my-pi 当成可随时替换的 adapter。
问题 推荐答案 原因
oh-my-pi 是 adapter 还是基座？ 基座 基于它打造 xuanpu-agent runtime 它已有 agent loop、provider、工具生命周期、compaction、overflow、session、subagent 和 CLI/SDK 能力，足以省去从零打造 agent 的主体工作。
是否整仓硬 fork？ 不建议 不做无边界 hard fork 上游迭代很快，2026-06-15 刚发布 v16.0.1。整仓硬 fork 会把 TUI、extensions、natives、settings、ACP 等全部升级风险拖进 Xuanpu。
是否保持薄 shim？ 不够 shim 只能解决 turn echo 等局部 bug Xuanpu 要做长期任务、UserRound、上下文稳态、审计和独立发行，需要拥有 runtime contract 和 session/context kernel。
是否现在升级 v16.x？ 拆开 先稳 15.2.4，另开 v16.x spike v16.0.1 有 coding-agent 层 breaking changes，也有 provider payload/tool-args 修复。升级有价值，但不应混入架构重排的第一步。
xuanpu-agent 是否独立于 Xuanpu Desktop？ 是 独立 CLI/SDK + 桌面嵌入双形态 产品定位保留：Xuanpu Desktop 提供更好的现场，但 agent core 必须能在外部项目目录独立运行。
上下文是否每次请求都重建？ 否 Segment 内连续累积，边界才重建 每次 provider request 都重建会破坏连续性和 prefix/cache 稳定性；默认应在 ContextSegment 内 append，接近预算或恢复边界时才 compact/rebuild。
大工具输出和图片如何处理？ 卸载 raw 内容归档，只给模型摘要和引用 100K 命令输出或 5MB 截图不能持续占用 live history。工具输出、截图和图片应进入 archive/media store，模型上下文只保留 observation ref、摘要、OCR 和关键事实。

2. 产品定位：沿用前序结论，但边界要升级

前序关于 xuanpu-agent 的产品定位基本成立：它是 Xuanpu 的原生 Agent 运行时，是 “现场感知 + 上下文稳态 + 成本地形治理”的产品化载体。需要调整的是与 oh-my-pi 的关系。 之前 spike 文档写过“no fork of oh-my-pi”，那适合第一阶段验证依赖是否能跑进 Electron。 现在已经进入产品化设计阶段，这条约束应被替换。

纠偏：“no fork of oh-my-pi”不再是长期目标。新的目标是 “有边界地 fork / vendor / patch oh-my-pi core 能力”，把上游成熟 agent workbench 变成 Xuanpu Agent 的底座，而不是继续把底层能力藏在 adapter 后面。

2.1 xuanpu-agent 应该独立发行

xuanpu-agent 不能只作为 Xuanpu Desktop 里的一个 runtime option 存在。更合理的产品边界是： 一个可独立安装、可在项目目录运行、也可被 Xuanpu Desktop 嵌入的 agent runtime。

形态 用户价值 依赖 Xuanpu Desktop 的程度
xuanpu-agent CLI 在任意 repo 中使用 Xuanpu 的上下文稳态、TaskRun、记忆和 oh-my-pi-derived tools/providers。 低。使用本地 Git/FS/AGENTS/配置/SQLite fallback。
Xuanpu Desktop embedded runtime 获得 worktree manager、Session HQ、XFP Field Packet、UI permissions、multi-worktree、terminal/test/focus 等更高质量现场。 高。Desktop 是增强环境 provider。
SDK/RPC/ACP bridge 允许其他编辑器或自动化系统驱动 xuanpu-agent，复用同一 agent core。 中。可借鉴 oh-my-pi 的 RPC/ACP 入口，但协议应保持 Xuanpu 自己的 TaskRun 和 ContextFrame 语义。

2.2 Xuanpu Desktop 提供现场，不垄断 agent

Xuanpu Desktop
  provides richer field:
    worktree graph, selected files, UI focus, terminal snapshots,
    Session HQ timeline, approvals, persisted XFP packets,
    memory proposals, task-run dashboard

xuanpu-agent core
  owns durable agent semantics:
    TaskRun, UserRound, ProviderRequest, ContextFrame,
    compaction, retrieval, checkpoints, cost budgets,
    tool observation archive, provider recovery

oh-my-pi-derived runtime
  supplies proven mechanics:
    Agent loop, stream providers, tool execution lifecycle,
    steering/follow-up, provider payload hooks,
    compaction primitives, overflow detection, native tooling ideas

这样划分后，Desktop 不是 xuanpu-agent 的“宿主壳”，而是最佳现场 provider。agent core 离开 Desktop 仍然可用，只是现场质量降级；进入 Desktop 则获得更高密度、更可审计的上下文。

3. 为什么 oh-my-pi 是合适基座

如果从零打造 agent，Xuanpu 至少要重做 provider streaming、tool-call loop、tool schema 修复、 session state、compaction、CLI/SDK/RPC、subagents、native tools、error recovery、provider quirks。 oh-my-pi 已经覆盖其中大量工程难点。

3.1 Agent loop 不是玩具实现

pi-agent-core 的 Agent 已经提供 streaming、tool calls、 steering/follow-up queue、busy guard、tool lifecycle hooks、telemetry hooks、payload hooks。 Xuanpu 只需要在边界上改造上下文和事件契约，而不是重写一个模型循环。

3.2 Provider quirks 已被持续打磨

pi-ai 不只是 OpenAI/Anthropic client。上游 release note 里大量修复都集中在 Responses payload hooks、streamed object tool arguments、nullable enum MCP schema、Cursor tool errors 等 provider/harness 边角问题。这些不是 prompt 能解决的。

3.3 Compaction 有真实 session 语义

上游 compaction 不是简单“总结一下旧对话”，而是 session entry、branch summary、 overflow retry、threshold maintenance、OpenAI remote compact preserve data 的组合。 这与 Xuanpu 的 TaskRun/Checkpoint/ContextFrame 可以合流。

3.4 Tool harness 值得继承

上游强调 read/search/edit/hashline/LSP/DAP/browser/subagents/native tools 等能力。即使 Xuanpu 不全量引入 TUI，工具执行生命周期、结果 coercion、native 工具方向和 subagent 协作模式也值得吸收。

3.5 多入口产品形态已被验证

README 中的 interactive、one-shot、RPC、ACP、SDK 入口说明 oh-my-pi 已经不是单一 CLI。 xuanpu-agent 要做独立发行，可以借它的产品结构经验，而不是自己摸一遍。

3.6 上游活跃，适合持续同步

2026-06-16 查询时上游当天仍有 push，最新 release 是 2026-06-15 的 v16.0.1。 这说明上游不是死库；我们需要可同步边界，而不是一次性复制。

4. 哪些东西不能外包给 oh-my-pi

以 oh-my-pi 为基座不等于放弃 Xuanpu 的产品内核。oh-my-pi 解决的是“成熟 agent harness 怎么跑起来”，Xuanpu 要解决的是“开发现场如何成为可治理的上下文操作系统”。以下能力必须由 Xuanpu 拥有最终语义。

能力 为什么不能直接交给 oh-my-pi Xuanpu 应拥有的出口
XFP / Field Packet oh-my-pi 知道项目文件和工具，但不知道 Xuanpu Desktop 的 worktree、focus、terminal、tests、Session HQ、multi-worktree 现场。 XfpPacketCompiler、FieldProvider、ContextFrameCompiler
TaskRun / UserRound oh-my-pi 的 session 更像 agent 会话流，Xuanpu 需要用户目标、lease、cost ceiling、pause/resume、checkpoint、overnight autonomy。 TaskRunScheduler、UserRoundRunner、LeasePolicy
Context Budget / 稳态策略 上游 compaction 解决长 session 可用性，Xuanpu 还要解决每个 provider request 的分区、prefix hash、included/omitted 审计。 ContextPacker、BudgetLedger、ProviderRequestSnapshot
Memory / Episode / raw refs Xuanpu 的记忆要求 scope、raw refs、proposal、可编辑可删除，且要和 Field Events、command traces 互相引用。 EpisodeStore、MemoryPageStore、RawRefResolver
Session HQ / UI 治理 oh-my-pi TUI 不是 Xuanpu UI。Xuanpu 要把修复、预算、compaction、task progress 显示在桌面产品的信息架构中。 CanonicalAgentEvent、Session HQ timeline、Context Budget Debugger
权限与工作区边界 Xuanpu 有 trusted worktree、dangerous path、Desktop permission prompt、跨 worktree 的写入风险。 ToolPolicy、PermissionService、WorktreeBoundaryGuard

5. 架构选项比较

选项 做法 优点 硬伤 结论
A. Shallow adapter 继续依赖 @oh-my-pi/pi-agent-core，只写 Xuanpu wrapper。 短期最快，上游升级简单。 无法拥有 session/compaction/user-round 语义；Xuanpu 专属 invariants 只能在外层补丁中绕路；每次上游行为变化都可能破坏语义。 否决
B. 整仓 hard fork 把 oh-my-pi monorepo 全部 fork 成 Xuanpu 版本。 控制力最大，可以任意改。 上游活跃，硬 fork 会带来巨大同步成本；TUI/extensions/natives/marketplace/ACP 等不属于当前核心路径。 不推荐
C. 从零重写 agent 只参考概念，Xuanpu 自己实现 provider/tool/loop/session。 架构最纯。 浪费开源基座；provider/tool streaming/compaction 细节会吞掉大量时间；用户明确不希望从零造。 否决
D. 产品化 fork-core 选定 pi-agent-core、pi-ai、compaction/session 相关模块作为受控源代码边界，Xuanpu 增加自己的 runtime contract。 保留上游成熟度和同步能力，同时能拥有 Xuanpu 语义。 需要建立 upstream sync discipline、diff audit、版本矩阵和接口收敛。 推荐
具体化：D 不是“复制几个文件然后改到不可维护”。它应该是一个可审计的 fork-core： 每次升级记录 upstream tag/commit、保留 patch queue、用 contract tests 锁住 Xuanpu 行为， 对外暴露 @xuanpu/agent-core 而不是任由业务代码到处 import 上游内部路径。

6.1 核心运行对象

对象 定义 当前映射 建议调整
TaskRun 用户希望 agent 完成的一个 durable objective，可暂停、恢复、跨多轮、跨 checkpoint。它不是 agent 的 task list，而是 Xuanpu 的任务运行账本。 AgentTaskRun 已存在。 保留，抽出 Desktop-independent scheduler。
Plan / TodoList agent 为当前目标生成的执行计划和步骤清单，可动态更新、展示、审批或标记进度。 Claude Code/Codex/pi 均已有类似能力；Xuanpu 已有 plan.ready 事件。 复用并标准化为 TaskRun 内的可见计划产物，不把它当作 TaskRun 本身。
UserRound 一次用户意图或 agent-authored continuation 的语义单位。一个 UserRound 内可以包含多个 ContextSegment，每个 Segment 内有多个 provider requests。 当前 turn 与 prompt() 混在一起。 新增显式 UserRound，把用户输入、pending continuation、recovery continuation 统一建模。
ProviderRequest 一次真实发给 provider 的请求，包含 system、context messages、prompt、tools、model、budget、provider session policy。 XuanpuProviderRequestSnapshot 已存在。 提升为 agent-core contract，作为 replay/audit 的单一事实。
ContextFrame 在 UserRound 起点或 Segment 边界生成的稳定上下文编译结果，包含 zones、prefix hash、included/omitted、raw refs。 packContext() output + XFP packet + context package 分散存在。 合并为 ContextFrame，再转 provider messages。
ContextSegment / Epoch 一段不做全量 rebuild、连续累积 messages/tool results 的 provider-call 区间；结束时才 checkpoint/compact/rebuild。 AgentEpoch 已存在，且暴露在 task-run 技术设计中。 DB 可保留 epoch，产品和文档中逐步改称 ContextSegment，避免让用户理解 epoch。
ToolObservation 一次工具调用后的可审计观察：摘要、exit code、耗时、raw output ref、压缩规则、digest。 已有 command trace、Token Saver、context compressor 雏形。 作为 Segment 内累积的默认内容，raw output 只按需读取。
ImageObservation 图片/截图被 vision 识别后的低成本替代物：path/ref、hash、尺寸、OCR、caption、关键 UI 事实。 ProviderRequest 记录已对 image 做 hash/content omitted，但缺少一等 media store。 新增 MediaOffloader；raw image 默认只允许进入一次 provider request。

  │
  ├─ TaskRunScheduler
  │    resolves task objective, autonomy, lease, cost ceiling, pending recovery

  ├─ FieldProvider
  │    Desktop: XFP field, focus, terminal, tests, multi-worktree, UI state
  │    CLI: git/fs/AGENTS/session notes fallback
  │

  │    compile initial ContextFrame at UserRound start or Segment boundary:
  │      stable anchor
  │      frozen episodes
  │      task state
  │      retrieved memory / episodes / workflows
  │      working set
  │      current field
  │      current request
  │
  ├─ ProviderRequestBuilder
  │    split contextMessages from promptMessage
  │    compute providerRequestHash and actualPrefixHash
  │    attach tools and providerSessionPolicy
  │
  ├─ ContextSegment
  │    reuse current ContextFrame
  │    append assistant/tool/user messages inside the segment
  │    do not run full ContextFrameCompiler per provider request
  │
  ├─ oh-my-pi-derived AgentLoop
  │    transformContext at provider boundary
  │    convertToLlm
  │    stream provider response
  │    route proposed tool calls through ToolCallGovernor
  │    execute tools with before/after hooks
  │    offload/compress raw tool output before it enters history
  │    evict raw image blocks after first vision request
  │    emit usage/tool/assistant events
  │
  ├─ Runtime governance
  │    record provider usage, tool traces, budget snapshots
  │    detect overflow/incomplete/no-progress
  │    compact/checkpoint at segment boundary
  │
  └─ Session/Event stores
	      persist assistant message, task state, memory proposals, UI events
关键修正：不要在一个 UserRound 内为每次 provider request 做全量上下文重建。 正常路径是 Segment 内连续累积；只有 UserRound 起点、Segment close、overflow recovery、 checkpoint resume、显式 refresh 或阶段切换时，才重新编译 ContextFrame。ProviderRequestSnapshot 仍然每次记录，但它是审计快照，不代表重新 pack。

6.3 Context kernel 与 oh-my-pi compaction 的合流

当前 Xuanpu 的 ContextPacker 和上游 compaction 分别站在两个层级：

层级 当前实现 职责 合流方式
Provider request context Xuanpu packContext() 为本次请求选择哪些 context zones，控制预算、prefix、审计。 继续由 Xuanpu 拥有，改名/升级为 ContextFrameCompiler。
Session history maintenance oh-my-pi CompactionEntry / BranchSummaryEntry 把旧 session history 重写为 summary，处理 overflow/threshold/idle/handoff。 移植为 Xuanpu SegmentCompactor，输出 episode/checkpoint/context-summary entries。
Durable memory Xuanpu memory page / episode block 带 scope、raw refs、retrievalReason、可编辑治理。 compaction 结果不能直接当长期记忆，必须经过 raw refs 和 proposal policy。

9. 上下文与长任务设计

用户提到的“上下文窗口怪异”和 liteLLM 本地中转问题不作为本方案主线，但它提醒我们： xuanpu-agent 不应该把 1M context 当常态依赖。产品级 agent 要默认在更保守的上下文预算中稳定运行。

9.1 三层预算

层级 目标 建议默认 处理策略
Managed Context Xuanpu 编译出来的 ContextFrame token 估算。 Focused 80K、Balanced 150K、Extended 200K。 ContextFrameCompiler 控制 zones；超过阈值时减少 working set/retrieval。
Provider Estimated Input managed context + system/tools/provider overhead。 常态低于 150K 到 200K；经 gateway 时避免贴近 250K。 ProviderRequestBuilder 估算并记录；高风险 provider 自动降 profile。
Provider Actual Usage provider 返回的真实 input/cache/output。 作为校准，不作为唯一真相。 写 usage ledger；发现 usage input > window 或 overflow pattern 时触发 compaction/retry。
精确说明：OpenAI 官方文档显示 GPT-5.5 的 context window 是 1,050,000 tokens；272K 是 long-context 的计费/档位分界，不是模型硬上限。 因此“在 272K 左右触发压缩”如果发生在 OpenAI 正路由上，通常更像是应用层、代理层、预算策略或 自动压缩器的阈值，而不是模型本身只到 272K。

9.2 ContextFrame zones

ContextFrame
  stable prefix
    1. Anchor
       Xuanpu rules, worktree identity, stable task invariants
    2. Frozen Episodes
       compacted history with raw refs, immutable inside segment

  volatile middle
    3. Task State
       current objective, recent steps, blockers, decisions
    4. Retrieved Memory / Episodes / Workflows
       gated by current user request, every item has retrievalReason
    5. Working Set
       recent high-fidelity turns, deduped against episodes

  volatile suffix
    6. Current Field
       live XFP packet, git/focus/terminal/tests/multi-worktree
    7. Current Request
       the only prompt-echoed user message

  implicit
    8. Buffer
       reserved for tool results, model output, provider overhead

9.3 Segment/Epoch 策略

现有实现已经把 pre-flight freeze 从每 turn 挪走，并倾向在 epoch/soft-shrink 边界更新 frozen episodes。 这个方向应该保留。新的策略是：

  1. 一个 UserRound 开始时先构建一次初始 ContextFrame，启动 ContextSegment。
  2. 同一 Segment 内允许 oh-my-pi agentLoop 累加 messages 和 tool results，保留连续性和 provider cache 友好性。
  3. 同一 Segment 内不运行全量 ContextFrameCompiler；ProviderRequest 只追加当前段内新增内容。
  4. 到 Segment 边界才做 checkpoint/compact/freeze/rebuild，避免每个 provider request 都重建 prefix。
  5. Segment 边界由 projected next request tokens、provider call count、fill ratio、lease、no-progress、cost ceiling、risky write 共同决定。
  6. Segment summary 进入 FrozenEpisodes 或 Checkpoint，不直接伪装成用户消息。
  7. 下一 Segment 从新的 ContextFrame 开始，prefixHash 变化必须可解释。
UserRound
  ├─ ContextSegment #1
  │    ProviderRequest 1
  │    ProviderRequest 2
  │    ProviderRequest 3
  │    ... append within segment, no full rebuild
  │
  ├─ boundary: projected tokens near limit / overflow / checkpoint / recovery
  │    compact old segment
  │    write checkpoint + raw refs
  │    compile next ContextFrame once
  │
  └─ ContextSegment #2
       ProviderRequest 4
       ProviderRequest 5

9.4 工具调用过滤、输出卸载与图片卸载

Segment 内连续累积的前提是：不能让高噪声工具调用、100K 级命令输出或 5MB 截图直接进入 live history。 因此需要把 Token Saver 从局部 Bash 包装升级为 xuanpu-agent 的一等 harness 能力。 当前仓库已有 src/main/services/token-saver/ 雏形，策略注释明确说明借鉴 RTK 的规则库思想，并已实现 ANSI 清理、进度去重、NDJSON 摘要、失败聚焦、统计提取等高 ROI 规则。

能力 职责 进入模型的内容 原始内容去向
ToolCallGovernor 在工具执行前 allow/rewrite/deny/route/ask。过滤危险、重复、无意义或会产生巨大输出的调用。 被允许或改写后的工具调用；拒绝时返回原因和建议替代命令。 记录 governor decision 到 audit/event ledger。
OutputCompressionPipeline 对工具输出做规则化瘦身：strip ANSI、collapse progress、failure focus、stats extraction、NDJSON summary。 摘要、head/tail、失败片段、统计行、rule hits。 压缩前输出交给 offloader 或 command trace。
ToolOutputOffloader 超过阈值的 stdout/stderr/MCP result 不进上下文；写入 archive，返回 ToolObservation。 exit code、耗时、bytes、摘要、archive path/logical ref、sha256、可按需读取提示。 ~/.xuanpu/archive 或 command trace store；后续通过 budgeted reader 局部读取。
MediaOffloader 图片、截图、浏览器快照、视觉测试截图先归档；raw image block 默认只允许进入一次 vision request。 ImageObservation：path/ref、hash、bytes、mime、dimensions、caption/OCR、关键 UI 事实。 media archive；需要精查时通过 xuanpu_view_image(ref, crop) 或 OCR/region reader。

10. 实施路线

实施上不要一次性重排整个工程。先把“oh-my-pi-derived runtime 是基座”这个事实固化为包边界和 contract tests， 再从 Desktop implementer 里逐步抽出 agent-core。

Phase 0：基线冻结与事实记录

  • 在 @xuanpu/pi-agent-core 增加 upstream metadata，明确当前基线为 oh-my-pi 15.2.4。
  • 把 runTurn() 的行为写成 contract test：context messages 不 prompt-echo、fresh Agent per turn、providerSessionState 默认 disabled。
  • 把 v16.0.1 release note 中与我们相关的 fixes 建立 upgrade checklist：payload replacement、streamed object tool args、strict schema nullable enum、AgentSession streaming busy guard。
  • 不在此阶段升级 v16.x，避免把架构边界变化和上游升级风险混在一起。

Phase 1：从 shim 变成受控 fork-core

  • 新建或重命名为 packages/xuanpu-oh-my-pi-runtime，保留 @xuanpu/pi-agent-core 作为兼容 alias。
  • 把需要拥有行为的模块纳入受控源码边界：Agent facade、agentLoop wrapper、compaction pure functions、overflow detection、selected provider bridge types。
  • 业务代码只通过 loadPiAgentCoreModule() 或新的 runtime facade 访问，不再直接依赖上游包的行为细节。
  • 保留上游 re-export，但每个 Xuanpu-owned contract 都要有测试。

Phase 2：抽出 @xuanpu/agent-core

  • 从 xuanpu-agent-implementer.ts 中抽出 TaskRunScheduler、UserRoundRunner、LeasePolicy、ProviderRequestRecorder。
  • 定义 UserRound 类型，区分 user-originated、agent-continuation、recovery-continuation。
  • 把现有 AgentEpoch 的产品语义收敛到 internal ContextSegment，DB 可暂时沿用 epoch 命名。
  • 让 Desktop adapter 只负责 FieldProvider、IPC、UI event emission，不再承载 long-task orchestration。

Phase 3：ContextFrame 合流

  • 把 packContext() 输出升级为 ContextFrame，包含 zone decision、prefixHash、raw refs、retrieval ledger。
  • 把 oh-my-pi compaction 的 firstKeptEntryId、preserveData、file operation details 映射到 Xuanpu episode/checkpoint 模型。
  • 实现 SegmentCompactor：支持 context-full、handoff、provider-native compact、rule-based fallback。
  • 统一 overflow/incomplete/threshold/idle 四类维护路径，并写入 Session HQ timeline。
  • 明确 ContextSegment 内不做全量 rebuild；ProviderRequestSnapshot 每次记录，但 ContextFrame 只在 UserRound 起点或 Segment 边界生成。
  • 把 src/main/services/token-saver/ 提升为通用 ToolOutputOffloader，接入 Bash、read/search、test/build、MCP result 和 subagent output。
  • 新增 MediaOffloader 与 ImageObservation：图片/截图只在首次 vision request 中进入 raw media，之后以 path/ref + OCR/caption/facts 参与上下文。

Phase 4：独立 CLI 与降级 FieldProvider

  • 实现 @xuanpu/agent-cli：读取项目目录、AGENTS/Codex/Claude/Copilot 规则、Git 状态、本地 SQLite。
  • CLI 复用 @xuanpu/agent-core 和 @xuanpu/oh-my-pi-runtime，不复制 Desktop implementer。
  • CLI 事件输出采用同一 CanonicalAgentEvent，方便未来导入 Session HQ。
  • 先支持 one-shot/interactive，RPC/ACP 后置。

Phase 5：v16.x 升级评估

  • 单独开 oh-my-pi-v16-upgrade spike，对比 15.2.4 与 16.0.1 的 public behavior。
  • 重点跑 provider/tool contract：Responses payload hook、tool args merge、schema normalization、compaction docs 中的 new strategies、AgentSession busy behavior。
  • coding-agent 层 breaking changes 只在引入 CLI/extensions 时处理，不阻塞 core runtime。
  • 升级成功后更新 upstream metadata 和 patch queue。

Phase 6：产品硬化

  • Session HQ 展示 TaskRun/UserRound/Segment/ProviderRequest 四层状态。
  • Context Budget Debugger 支持回放某个 ProviderRequestSnapshot 实际看到了什么。
  • Memory proposal 与 raw refs 审计打通。
  • 提供一键导出 task-run report，便于失败复盘和模型/预算调优。

12. 测试与验收标准

12.1 Contract tests

  • runTurn：context messages 不产生 message_start/message_end prompt echo。
  • fresh Agent：同一 hive session 的两个 turn 不能共享 providerSessionState。
  • ProviderRequestSnapshot：相同输入 hash 稳定，timestamp 等 volatile 字段不影响 hash。
  • ContextFrame：stable prefix 只随 anchor/frozen episodes 改变，CurrentField 不污染 prefix。
  • Overflow detection：覆盖 OpenAI/Anthropic/Google/OpenRouter/Kimi/HTTP 413/usage silent overflow。
  • Compaction threshold：复刻上游 contextWindow - max(15%, reserve) 行为，并验证 Xuanpu override。
  • Segment rebuild：同一 ContextSegment 内多次 ProviderRequest 不重新运行全量 ContextFrameCompiler。
  • Tool output offload：100K stdout/stderr 必须返回 ToolObservation，raw output hash 与 archive 内容一致。
  • Media eviction：图片首轮 vision 后，下一次 ProviderRequest 不再包含 raw image block，只包含 ImageObservationRef。

12.2 Integration tests

  • mock streamFn，模拟多次 provider calls + tool results + followUp，验证 UserRound 内累加和 Segment 边界 compact。
  • 模拟高噪声工具调用：cat huge.log、find .、全量测试命令应被 ToolCallGovernor 改写、拒绝或加约束。
  • 模拟 5MB 截图：首次请求允许 vision，后续请求仅保留 path/hash/OCR/caption/facts，并确认 provider session 不保留 raw media。
  • 模拟 no-progress recovery：有 concrete tool progress 时继续，无 progress 时暂停，覆盖当前已修过的 watchdog 语义。
  • 模拟 gateway context limit：在 220K/250K 附近触发降 profile、compact 或 pause，而不是直接把请求打到 provider。
  • 模拟 OpenAI remote compact preserve data，确认 replay/audit 不丢 provider-native history。

12.3 Product acceptance

  • Desktop 中每个 TaskRun 可查看：UserRound、ProviderRequest、ContextFrame、usage、checkpoint、compact event。
  • CLI 中同一 agent core 可以完成 read/search/edit/test 的基本 coding loop。
  • oh-my-pi upstream 小版本升级后，contract tests 能指出行为差异，而不是靠人工试用发现。
  • 长任务不依赖 1M window：Balanced 默认 150K 可持续运行，Extended 作为显式选择。
  • Session HQ 可展开被卸载的工具输出和图片原件，但模型默认只看到摘要和 ref。

13. 风险登记

风险 严重度 表现 缓解
上游快速漂移 高 v16.x 已有 breaking changes，后续 provider/tool fixes 仍会持续进入上游。 upstream metadata + patch queue + contract tests + 单独 upgrade spike。
fork 过深导致不可同步 高 为了 Xuanpu 语义修改太多上游核心文件，后续无法吸收 fixes。 只 fork selected runtime subset；Xuanpu 语义尽量放 facade/context kernel；每个 patch 有名字和测试。
compaction 语义冲突 中高 oh-my-pi compaction summary、Xuanpu episode、memory page、checkpoint 互相重叠。 明确层级：compaction 是 session maintenance，memory 是 proposal + raw refs，checkpoint 是 task recovery。
provider/gateway 长上下文不稳定 中高 本地中转、liteLLM、OpenAI-compatible provider 在 250K 左右失败或误报。 默认 150K Balanced，220K 左右预维护，250K 前硬降级/compact，不依赖 1M。
工具输出 / 图片长期污染上下文 高 100K 命令输出或 5MB 截图如果持续留在 history 中，会迅速挤爆窗口并破坏连续性。 ToolCallGovernor + ToolOutputOffloader + MediaOffloader；raw 输出和 raw media 默认只短暂进入一次 provider request。
prefix cache 与动态现场冲突 中 每 turn 更新 field/frozen episodes 导致 prefix hash 频繁变化。 严格区分 stable prefix 与 volatile suffix；frozen episodes 只在 Segment 边界进入 prefix。
Desktop coupling 过强 中 agent core 离开 Electron main 无法运行。 FieldProvider abstraction；CLI provider 使用 git/fs/local SQLite fallback。
用户可见概念过多 中 TaskRun、Epoch、Turn、ProviderCall、ContextFrame 同时暴露会让产品难懂。 产品层只暴露 TaskRun、UserRound、Context Usage；Epoch 改为内部 Segment。

14. 需要沉淀为架构决策的事项

  1. ADR-1：xuanpu-agent 是 oh-my-pi-derived runtime。 不再使用“no fork of oh-my-pi”作为长期约束。
  2. ADR-2：当前基线继续 pinned at 15.2.4。 v16.x 升级单独 spike，不能和架构抽层混合。
  3. ADR-3：Xuanpu owns final ContextFrame。 oh-my-pi 可以提供 compaction/session mechanics，但最终 provider request messages 由 Xuanpu 记录和审计。
  4. ADR-4：Provider session 默认 disabled。 provider-native continuation 只作为可 replay 的受控例外。
  5. ADR-5：UserRound 成为产品语义，Epoch/Segment 成为内部工程语义。 当前 DB 可以兼容，但 UI 和文档应逐步调整。
  6. ADR-6：上下文预算默认保守。 Balanced 150K 是常态目标，Extended 200K 是显式选择，1M 是 fallback 不是产品依赖。
  7. ADR-7：ContextSegment 内默认累积，不做 provider-request-level rebuild。 ContextFrame 只在 UserRound 起点、Segment 边界、overflow/recovery、checkpoint resume 或显式 refresh 时重建。
  8. ADR-8：所有高噪声工具调用必须经过 ToolCallGovernor。 工具执行前支持 allow/rewrite/deny/route/ask，避免无约束 Bash/read/search/test 把上下文打爆。
  9. ADR-9：raw tool output 与 raw media 默认 offload。 模型上下文只接收 ToolObservation/ImageObservation；原始输出、截图和图片以 raw refs 归档并可按需局部读取。
